# PDF 不稳定及向量化慢的只读排查

证据取自本地运行后端 PID 1292 的持久日志 `technical-advisor-app/data/logs/backend.log`、当前 PostgreSQL 文档/页面/已发布切片记录及现行实现。时间均为 Asia/Shanghai。未重跑文档、未调用模型、未改配置或重启服务。

## 07C 失败原因已确认

文档 `17540e13-94b6-473d-800c-c8d33859f6ec`：

- 20:41:47 开始处理；20:43:10 第7页报 `model_timeout`，页调用耗时60079ms，随后全文失败。
- 20:44:31 再次处理；20:45:31 同一第7页再次 `model_timeout`，耗时60072ms，全文失败。
- 数据库第7页状态 failed、警告 `[model_timeout] 模型请求超时`；其他7页 ready、1页 blank。本次没有发布向量，符合整篇成功才发布的规则。
- 原页可提取382字符，但视觉调用失败后未用该部分文本冒充整页完整。失败发生在PDF视觉解析，不是该文档的向量化阶段。
- 当前 PDF 角色为 `deepseek-v4.1-flash`，经已配置火山兼容端点调用；07B 本轮第1页和第5页也出现约60秒的同类超时，不能把问题归为07C独有的文件损坏。

KnowledgeModelHttp 目前连接10秒、单次HTTP25秒、整个HTTP调用60秒；瞬态错误最多2次退避重试。上述60秒是调用预算耗尽，不等于已证明供应商排队、限流或每次重试具体次数。超时没有供应商request-id，现有日志不能区分上游慢、代理/网络等待及各次重试占用。

## 向量化存在已证实的串行与碎片放大

- 当前配置4个文档worker，用于不同文档并行；DocumentIngest 的单文档嵌入仍是 for循环逐片 embed(...).block(65s)，等待上一片完成再处理下一片。
- KnowledgeEmbeddingModel 每次 `/embeddings` 请求只传一条文本，尚无批量或单文档有界并发。
- 07A 已就绪，发布56片、合计2918字符；平均52.1字符，最短4字符，49片不足100字符。9页不等于9次向量化：这份文档实际执行56次逐片调用。
- PdfContent 对各个块分别切片，跳过页眉页脚，但未合并相邻短块，因此小标题/短段落容易成为独立请求。即使模型识别很快，网络请求固定开销仍会累计。
- 当前向量端点的模型为 `doubao-embedding-vision`，与PDF解析模型不同。此处没有验证其批量接口能力，不能直接假定支持任意批大小。
- 07A 此次20:41:45开始、20:44:34完成，整篇168955ms。日志仅有整篇耗时，缺解析结束/向量化开始、逐批耗时，所以不能把169秒全部说成向量化耗时。
- 排查时 PostgreSQL 没有非idle业务查询或锁等待；这是当前快照，不能排除历史短暂数据库等待，更不能据此证明整个阶段只慢在网络。

## 对症改进顺序

1. 为解析和向量化分别记录阶段起止、片段/批数、已完成量和模型调用耗时；重试记录安全原因及次数，避免之后再次依赖猜测。
2. 将视觉解析与嵌入的超时/重试预算分开，并对同端点限制总并发。先用失败页证据确认预算和供应商等待，而不是盲目增加线程或无限延长超时。
3. 核实当前供应商支持的嵌入批量能力；支持则批量，否则使用全局受控的小并发。避免每篇独立加并发导致4篇文档相乘放大请求。
4. 合并同页相邻短正文块，同时保留来源映射、表头/表格边界及数字证据；展示已向量化x/y，最终仍整篇原子发布。

这次只完成原因排查，没有实施以上改动，也没有声称已解决供应商超时。
