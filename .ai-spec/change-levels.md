# 改动分级与处理流程

任何改动开始前，必须先按下表判定等级；无法确定时按较高等级处理。等级只升不降：执行中发现影响范围超出原判定时，立即停止并按新等级重新走流程。

## 一、低级改动

**定义**：影响范围限于单一模块内部、无公共接口变化、无用户可见行为变化、风险低。

**典型场景**：
- 前端 UI 样式微调、文案修改（经 i18n 词典）、纯展示优化
- 补充或改进测试、修复明显的实现笔误
- 不改变行为与签名的内部实现整理
- 文档、注释、示例代码修正

**处理流程**：直接编码实现，完成后通过对应领域门禁（见 `backend/gates.md` 或 `frontend/gates.md`）。

## 二、中级改动

**定义**：涉及多模块交互、内部接口变更、用户可见行为变化，或具有一定复杂度。

**典型场景**：
- 模块内部 API / SPI 变更，或跨模块调用关系调整
- 业务逻辑调整、错误处理行为变化
- 依赖版本升级（minor / patch）
- 前端新增功能页面或跨 feature 的组件调整
- Go 控制面内部接口或存储结构（migration）调整

**处理流程**：编码前必须先产出实施计划并纳入改动说明，包含：
1. 改动范围：涉及模块/文件清单、不变的部分
2. 实施方案：关键设计点与替代方案取舍
3. 测试方案：新增/修改的测试及验证命令
4. 文档影响：用户可见行为变化须同步更新 `docs/v2` 对应 EN 与 ZH 页面及受影响示例

## 三、高级改动

**定义**：涉及核心架构、公共契约、跨系统交互或重大功能变更。

**典型场景**：
- `deepscope-core` 公共 API：公共构建器、接口签名、序列化状态格式、事件 payload
- 核心运行时语义：Reactor 取消/错误/清理行为、中间件链顺序、权限检查、`call()` 与 `streamEvents()` 终态一致性
- 模块依赖方向调整、新增/移除 Maven 模块或扩展模块
- 依赖大版本升级、Java/React 等平台版本变化
- 破坏性变更（任何形式）

**处理流程**：必须编写完整实施方案，经人工评审确认后方可执行。方案在中级实施计划四项基础上，还需包含：
5. 兼容性分析：公共 API / 序列化状态 / 事件 payload / CRD / proto 的兼容性结论与迁移路径
6. 回滚方案
7. 分阶段执行与验证节点

## 四、通用改动流程（所有等级必经）

以下步骤与等级无关，任何改动都必须执行：

1. **动手前**：查看 `git status` 与相关代码确认现状；明确公共行为、兼容性影响与改动范围。
2. **判级**：按上文一/二/三判定等级并执行对应流程；执行中发现影响超出原判定，立即停止并按新等级重走流程。
3. **契约先行**：跨前后端改动须先定义 API 契约（路径、方法、请求/响应类型、错误码），经确认后再各自实现；纯前端或纯后端改动不受此约束。
4. **实现 → 测试 → 自检完整 diff**：逐文件检查改动内容，确认只含任务相关变更。
5. **文档同步**：用户可见行为变化必须更新 `docs/v2` 对应 EN 与 ZH 页面及受影响示例。
6. **收尾检查**：无无关文件混入、无生成产物误提交（如 `target/`、`node_modules/`）、无格式错误、无密钥/凭据。
7. **门禁**：按验证矩阵执行对应命令；跨模块或公共契约变更必须全量检查。
8. **提交纪律**：未经用户明确授权，不 commit、不 push；提交格式遵循 [collaboration.md](collaboration.md)。

## 五、验证矩阵

| 等级 | 门禁要求 |
|---|---|
| 低级 | 受影响模块测试 + 格式检查（Java：`mvn -T1 -pl <module> -am test` + `spotless:check`；前端：`npm test` + `npm run lint`；Go：`make test`） |
| 中级 | 受影响模块门禁 + 相邻模块测试 + 相关 `docs/v2` EN/ZH 同步更新 |
| 高级 | `mvn -B -T1 clean verify` 全量通过（Java 契约变更）；Go：`make verify` zero-diff + `make test`；涉及扩展模块结构时运行 `.github/scripts/check-shade-and-bom-sync.sh`；人工评审通过 |

本文件覆盖改动分级与通用流程；AI 协作行为规则（沟通方式、编辑原则、报告格式）见 [collaboration.md](collaboration.md)。
