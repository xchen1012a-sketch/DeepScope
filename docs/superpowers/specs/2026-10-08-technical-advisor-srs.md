## 1. 项目概述

### 1.1 背景

本项目是一个**个人简历演示作品**，用于求职展示。作者具备约半年 AI 业务系统开发经验，求职方向为 AI 开发 / Java AI 应用开发岗位。

目标访客为技术面试官、技术负责人、同行开发者。此类访客的核心疑问是：**候选人是"会调用大模型 API"，还是"真正理解 Agent 工程"**。本作品的首要任务是回答这个疑问。

### 1.2 项目定位（一句话）

> **访客给出一个技术对象，系统自行判断该做什么、自己组织团队去查、最后交付一份每个结论都能追溯到依据的技术判断。**

### 1.3 项目目标

| 编号 | 目标 | 说明 |
| --- | --- | --- |
| G1 | 展示自主拆解能力 | 同一输入，复杂度不同则拆法不同，且拆解过程对访客可见 |
| G2 | 展示动态组队能力 | 派几个子智能体、派谁，由主智能体运行时判断，而非代码写死 |
| G3 | 展示可扩展架构 | 新增专精领域不需要改代码，只需新增技能；且访客可自助新增 |
| G4 | 展示工程完备性 | 依据追溯、过程可视化、会话持久化、人在环路、权限边界 |
| G5 | 公网可用 | 部署于作者自有云服务器，访客可直接访问使用 |

### 1.4 非目标（明确不做）

以下内容**明确排除**在本期范围之外，任何一条的加入都需要重新评审：

| 编号 | 非目标 | 原因 |
| --- | --- | --- |
| N1 | 多租户 / 账号登录体系 | 演示不需要；公网防护改用限流与配额 |
| N2 | 团队协作 / 工作流编排 | 属框架预览版平台能力，部署成本高，风险大 |
| N3 | 三个专精领域各自独立的界面 | 三个领域共用一套界面，仅提示语与结果模板不同 |
| N4 | 使用任何来自作者前雇主的系统、数据或设计细节 | 知识产权风险，且对面试官构成负面信号 |
| N5 | 分布式 / 多副本部署 | 单机即可满足演示需求 |

### 1.5 目标用户

| 角色 | 描述 | 核心诉求 |
| --- | --- | --- |
| 访客（主） | 技术面试官、技术负责人 | 快速判断候选人的 Agent 工程能力 |
| 访客（次） | 同行开发者 | 拿到对自己有用的技术结论 |
| 作者 | 系统所有者 | 通过演示获得面试机会；控制运行成本 |

### 1.6 成功标准

| 编号 | 标准 | 可验证方式 |
| --- | --- | --- |
| S1 | 访客在 3 分钟内能看懂"这个系统在做什么" | 找 3 位非本人测试者，观察其是否能自述系统用途 |
| S2 | 访客能亲眼看到主智能体的拆解与派兵过程 | 演示全程无"卡住不动"的黑盒期 |
| S3 | 访客能独立完成一次自定义专精领域 | 无引导情况下完成 F14 全流程 |
| S4 | 任意输入都能得到合理回应，无一例拒绝 | 见 F04 验收标准 |

## 2. 术语表

| 术语 | 定义 |
| --- | --- |
| 主智能体 | 系统的唯一入口智能体，承担判断、拆解、调度、汇总职责 |
| 子智能体 | 由主智能体在运行时派出的执行单元，拥有独立上下文 |
| 技能 | 领域知识包。一份说明文件 + 可选参考资料与脚本，描述"这类问题该怎么处理" |
| 专精领域 | 一份技能所覆盖的问题类型。本系统预置三个 |
| 通用模式 | 输入未命中任何专精领域时的兜底处理路径 |
| 交付物 | 一次任务完成后产出的结构化结论，是"任务完成"的唯一凭证 |
| 依据 | 支撑某条结论的原始事实来源（文件、代码片段、查询结果） |
| 草稿技能 | 尚未通过审核、未上线的技能 |

## 3. 总体设计

### 3.1 架构原则

| 编号 | 原则 | 说明 |
| --- | --- | --- |
| P1 | **知识放技能，执行按需分配** | 主智能体承载"怎么判断"，执行既可以自己做，也可以派子智能体。两层分离指的是**知识与执行分离**，不是"主智能体不动手" |
| P2 | **永不拒绝，只做分流** | 任何输入都有出路。区别只在走哪条路，不存在"不支持" |
| P3 | **扩展靠加文件，不靠改代码** | 新增专精领域 = 新增技能文件。这是架构可扩展性的验收口径 |
| P4 | **结论必须可追溯** | 没有依据的结论视为缺陷 |
| P5 | **过程必须可见** | 不可见的过程等于没有发生 |
| P6 | **动态优先于预设** | 凡是"预先写死的角色分工"都视为设计缺陷 |
| P7 | **派兵是手段，不是目的** | 派发子智能体本身有开销。简单任务主智能体自己做更快；仅在需要独立上下文、并行执行、或长任务时才派发 |
| P8 | **输入全选填，不设阻断项** | 任何单一输入都不得成为完成任务的前置条件。缺什么信息由主智能体判断是否追问，而不是由表单强制 |

### 3.2 系统分层

```
┌─────────────────────────────────────────────┐
│  交互层   会话界面 / 过程可视化 / 人在环路确认  │
├─────────────────────────────────────────────┤
│  交付层   结构化交付物 / 依据追溯 / 追问       │
├─────────────────────────────────────────────┤
│  内核层   主智能体                             │
│           ├─ 任务识别与兜底路由                 │
│           ├─ 自主拆解                          │
│           ├─ 动态组队（派子智能体）             │
│           └─ 汇总与判断                        │
├─────────────────────────────────────────────┤
│  能力层   技能库（领域知识）                    │
│           工具集（读文件/搜代码/抓网页/…）       │
│           子智能体池（通用 + 动态创建）          │
├─────────────────────────────────────────────┤
│  支撑层   会话持久化 / 权限边界 / 审计与限流     │
└─────────────────────────────────────────────┘
```

### 3.3 核心概念关系

- **主智能体**是唯一入口。它负责判断、拆解、汇总，并**按需决定**：这件事自己顺手做完，还是派人去做。
- **技能**挂在主智能体上，决定它"面对这类问题时的判断方法"。
- **子智能体**由主智能体运行时派出，每个拿到**各自定制的上下文**。派发是可选项，不是必经步骤。
- **工具**是手脚，主智能体和子智能体都能用。
- **专精领域**就是"一份技能"，且比通用模式**更细致**——它可以自带判断维度、执行路径、知识库与交付模板。预置三个，访客可自助新增。
- **通用模式**不是"降级处理"，而是**没有专精配置时的通用执行路径**：复杂输入同样可以走完整的分析与执行，只是没有领域专属的判断标准和交付模板。

### 3.4 数据流

```
访客输入
   ↓
[F04 任务识别] ──命中专精领域──→ [加载对应技能]
   │                                    ↓
   └──未命中────→ [通用模式]      [F05 自主拆解]
                        │               ↓
                        │        [F06 动态组队] ──→ 子智能体（并行/后台）
                        │               ↓                    ↓
                        │        [F07 依据追溯] ←────── 事实结果
                        │               ↓
                        └──────→ [F09 结构化交付]
                                        ↓
                              [F10 追问] / [F11 过程可视化]
```

### 4.2 输入层

#### F01 · 仓库尽调

| 项 | 内容 |
| --- | --- |
| 优先级 | P0 |
| 描述 | 输入一个公开代码仓库链接，产出该仓库的尽调报告 |

**Input**（全部选填，不得作为阻断条件）
- 代码仓库地址（GitHub / GitLab 等公开仓库）
- 访客关注的侧重点（如"只看安全"）
- 其他补充材料（技术栈说明、背景信息等）

> 若访客只说了"帮我看看这个项目"却没给地址，主智能体应**追问**或根据上下文推断，不得中断。

**Process**
1. 主智能体加载「仓库尽调」技能，按技能定义的判断维度组织工作
2. 自主拆解出待查维度（典型：项目定位、代码结构、依赖风险、许可证、社区活跃度、可维护性）
3. 为每个维度派出子智能体，各自携带定制上下文
4. 子智能体使用工具获取事实（读代码、读依赖清单、查提交记录、查议题等）
5. 汇总事实，按技能定义的判断标准形成结论

**Output**
- 一份尽调报告，固定包含：项目定位 / 关键事实 / 风险清单（按严重度排序）/ 总体结论与建议
- 每条结论附带依据引用

**验收标准**
1. 提供 3 个不同类型的公开仓库（活跃项目、半停滞项目、存在已知风险依赖的项目），**每个都能产出结构完整的报告**
2. 报告中的关键事实**与仓库实际状态一致**（人工抽查 5 条事实，命中率 100%）
3. 对"存在风险依赖"的仓库，风险清单中**必须包含**该风险
4. 单次任务在 **10 分钟内**完成（超时视为不达标）

**边界与异常**
- 仓库不存在或私有不可访问 → 明确告知原因，并建议可用的替代输入
- 仓库体积过大 → 应自行缩减调查范围并**说明缩减了哪些部分**

#### F02 · 方案设计

| 项 | 内容 |
| --- | --- |
| 优先级 | P0 |
| 描述 | 输入一个技术需求或想法，产出可落地的技术方案 |

**Input**（全部选填，不得作为阻断条件）
- 需求或想法的自然语言描述
- 已知的技术约束（现有技术栈、团队规模、预算等）
- 参考资料或参考实现

> 访客一句话也能开始。信息不足时由主智能体判断是否追问，而不是拒绝处理。

**Process**
1. 主智能体加载「方案设计」技能
2. 自主判断需要澄清的关键信息；信息不足以支撑方案时，**应先向访客提问**，而非凭空假设
3. 拆解出需要调研的方面（典型：技术选型、架构形态、关键取舍、风险）
4. 派出子智能体去核实选型的现实情况（公开资料、社区活跃度、已知坑）
5. 汇总成方案

**Output**
- 一份技术方案，固定包含：需求理解 / 候选方案对比 / 推荐方案与理由 / 架构要点 / 风险与缓解
- 每条选型建议附带依据

**验收标准**
1. 提供 3 个真实需求（如"给现有 Java 项目加 RAG""做一个多轮对话的客服"），**每个都能产出可执行的方案**
2. 方案中的**每个取舍都要给出理由**，不允许只列选项不给结论
3. 当输入信息明显不足时，**应先提问**；提问后补充信息能继续完成方案
4. 单次任务在 **10 分钟内**完成

**边界与异常**
- 需求本身不成立（如技术不可行）→ 应明确指出并说明原因，而非强行给出方案

#### F03 · 架构评审

| 项 | 内容 |
| --- | --- |
| 优先级 | P0 |
| 描述 | 输入一份已有的设计方案，产出评审意见 |

**Input**（全部选填，不得作为阻断条件）
- 待评审的设计方案描述（文本）
- 该方案所处的阶段（初稿 / 已上线）
- 相关代码仓库或文档地址

> 描述很简略时，主智能体应先指出缺少哪些信息并列出需要补充的内容，而不是拒绝评审。

**Process**
1. 主智能体加载「架构评审」技能（与 F02 共用领域知识）
2. 按技能定义的检查清单逐项对照
3. 对存疑项派出子智能体去核实（如"这个组件在目标规模下是否够用"）
4. 汇总为问题清单，标注严重度与修改建议

**Output**
- 一份评审意见，固定包含：总体评价 / 问题清单（含严重度：阻断 / 重要 / 建议）/ 每条的修改建议 / 结论

**验收标准**
1. 提供一份**预先埋入 3 个缺陷**的设计方案（如：未做上下文压缩、工具无权限边界、无失败恢复机制），**必须全部找出**
2. 问题清单中的每条都要**给出可执行的修改建议**，不能只指出问题
3. 严重度分级合理（阻断级问题不得降级为建议级）
4. 单次任务在 **10 分钟内**完成

**边界与异常**
- 输入描述过于简略，无法评审 → 应先指出缺少哪些信息，并列出需要补充的内容

### 4.3 内核层

#### F04 · 任务识别与兜底路由

| 项 | 内容 |
| --- | --- |
| 优先级 | P0 |
| 描述 | 对**任何**输入先做一次判断，决定走哪条路。**永不拒绝** |

**Input**
- 访客的任意输入（无格式要求，无必填项）

**Process**
1. 判断输入是否命中某个专精领域
2. **命中** → 加载对应技能，按该技能定义的**判断维度、执行路径与交付模板**处理
3. **未命中** → 进入**通用模式**。通用模式不是降级处理：主智能体同样可以自行分析、拆解、派发子智能体，走完整的执行路径，只是没有领域专属的判断标准与交付模板
4. 无论走哪条路，都应让访客**看出当前走的是哪条路**

> 专精领域与通用模式的差别，是**配置的细致程度**，不是"能不能做"。

**Output**
- 一个路由决策 + 该路径下的完整处理结果
- 一条对访客可见的模式标识（如"正在使用：仓库尽调"/"通用模式"）

**验收标准**
1. 三类专精输入各 3 个样例，**路由判断全部正确**
2. 对任意无关输入（天气、闲聊、百科问题），**均能给出合理回答，无一例拒绝**
3. 走通用模式时，访客**能明确识别**当前处于通用模式（不得伪装成专精分析）
4. 不得出现"抱歉，我只能处理技术类问题"之类的回复

**边界与异常**
- 输入为空白、乱码、超长 → 应给出合理回应并引导，不得报错或拒绝
- 输入同时命中多个领域 → 应选择最贴合的，或明确询问访客意图

#### F05 · 自主拆解

| 项 | 内容 |
| --- | --- |
| 优先级 | P0 |
| 描述 | 把任务拆解为子任务，并决定并行与依赖关系。**本功能是演示的核心看点** |

**Input**
- 路由决策结果 + 原始输入 + 已加载技能

**Process**
1. 依据技能定义的判断方法，识别出本任务需要查清的关键问题
2. 将问题组织为若干**互相独立**的子任务；存在依赖的应标注先后
3. **对每个子任务决定执行方式**：自己顺手做完（快），还是派子智能体（适合需要独立上下文、可并行、耗时长的任务）
4. 决定哪些子任务可并行、哪些必须串行
5. **产出拆解理由**（为什么这么拆、为什么这么分工），对访客可见

**Output**
- 一份子任务清单，每项含：目标、所需信息、预期产出、依赖关系、**执行方式（自办 / 派发）**
- 一段可展示的拆解说明

**验收标准**
1. **拆解规模随复杂度变化**：简单输入拆 1–2 项，复杂输入拆 4 项以上（同一类任务分别用简单/复杂样例验证）
2. 拆解过程与理由**对访客可见**（前端可展示）
3. 拆解结果中**不存在"预先写死的固定分工"**——即不同输入应产生不同的拆解结构
4. 子任务之间不得出现范围重叠或遗漏（人工评审）

**边界与异常**
- 任务过于简单，无需拆解 → 允许直接处理，但需说明"无需拆解"的理由

#### F06 · 动态组队

| 项 | 内容 |
| --- | --- |
| 优先级 | P0 |
| 描述 | 为每个子任务派出子智能体，且**每个子智能体拿到各自定制的上下文** |

**Input**
- F05 产出的子任务清单

**Process**
1. 对**决定派发**的子任务，创建或选择一个子智能体（决定自办的子任务不经过本功能）
2. 为该子智能体准备**定制上下文**：它要查什么、关注什么、边界在哪、交付什么格式
3. 派发执行（可并行、可后台）
4. 收集结果；后台任务完成后自动回到主智能体

**Output**
- 每个子任务一份事实结果
- 一份"派兵记录"（派了谁、给它的任务是什么、耗时多久）

**验收标准**
1. **每个子智能体收到的任务描述各不相同**（前端可见，人工抽查不得出现雷同的通用指令）
2. 多个子任务**并行执行**（可从时间线上观察到的重叠）
3. 后台任务完成后**自动回收**，主智能体无需轮询
4. 单个子智能体失败时，主智能体应**感知并处理**（重试或说明缺失），不得静默丢失
5. **同一输入重复执行两次，派兵数量与分工可以不同**（证明是动态而非写死）
6. **简单任务不派发**：给一个一句话就能答的问题，主智能体应自己完成，不派子智能体（可从过程视图观察到）

**边界与异常**
- 子智能体超时 → 应降级处理并说明
- 子智能体返回空结果 → 应识别并采取补救

#### F07 · 依据追溯

| 项 | 内容 |
| --- | --- |
| 优先级 | P0 |
| 描述 | 交付物中每条关键结论都必须能追溯到事实来源 |

**Input**
- 各子智能体返回的事实结果
- 主智能体的汇总结论

**Process**
1. 汇总时，为每条结论建立与事实来源的关联
2. 无法找到依据的判断，**必须降级**为"推测"或删除
3. 保留来源的可定位信息（文件路径、代码位置、查询内容）

**Output**
- 带依据标注的交付物
- 每条结论可展开查看来源

**验收标准**
1. 交付物中**每条关键结论都能展开看到来源**
2. 交付物中**不存在无依据的断言**（人工抽查 10 条结论，全部可追溯）
3. 依据引用**真实存在**（抽查 5 条依据，能对应到实际文件/查询）

**边界与异常**
- 来源不可公开引用 → 应说明"依据不可展示"而非编造

---

#### F08 · 动态创建子智能体

| 项 | 内容 |
| --- | --- |
| 优先级 | P1 |
| 描述 | 当现有子智能体能力不足时，主智能体自行创建新的子智能体定义 |

**Input**
- 执行过程中发现的"现有能力无法覆盖"的需求

**Process**
1. 主智能体识别出当前缺少某类专门能力
2. 自行撰写一份新的子智能体定义（职责、关注点、可用工具）
3. **经访客确认后**方可启用（人在环路）
4. 使用新子智能体完成任务

**Output**
- 一份新的子智能体定义
- 一条对访客可见的"新建子智能体"事件

**验收标准**
1. **至少能成功触发一次**（如尽调一个非 Java 项目时，自行创建对应技术栈的调查子智能体）
2. 创建过程**必须经过访客确认**，未确认不得启用
3. 新建的子智能体确实被用于本次任务并产生了结果

**边界与异常**
- 访客拒绝确认 → 主智能体应退回使用通用能力完成任务

### 4.4 交付层

#### F09 · 结构化交付

| 项 | 内容 |
| --- | --- |
| 优先级 | P0 |
| 描述 | 将子智能体结果汇总为固定结构的交付物 |

**Input**
- 全部子智能体的事实结果
- F07 的依据关联

**Process**
1. 按对应领域的模板组织内容
2. 合并、去重、消解冲突
3. 形成结论与建议

**Output**
- 一份结构化交付物（三个领域各有固定模板）

**验收标准**
1. **同一领域的多次交付，结构一致**（字段不缺失、不随意增减）
2. 三个领域各自的模板字段固定且互不混淆
3. 子智能体结果之间出现冲突时，交付物应**显式说明冲突**而非任选其一

#### F10 · 追问

| 项 | 内容 |
| --- | --- |
| 优先级 | P0 |
| 描述 | 交付完成后，访客可基于已有上下文继续追问 |

**Input**
- 访客的追问
- 本次会话的历史上下文与交付物

**Process**
1. 基于已有上下文回答
2. 若追问需要新的事实 → 应派出子智能体补充调查（而非凭空回答）
3. 补充调查的结果应**并入**本次交付物

**Output**
- 追问的回答
- （如有）更新后的交付物

**验收标准**
1. 追问**不重跑整个流程**（可从时间线上观察）
2. 追问时**记得前面查过什么**（如问"你刚说的那个依赖风险具体是什么"，能准确回答）
3. 需要新事实时**会去查**，不凭空作答

### 4.5 交互与可靠性层

#### F11 · 过程可视化

| 项 | 内容 |
| --- | --- |
| 优先级 | P0 |
| 描述 | 前端实时展示主智能体的思考、派兵与子智能体进度 |

**Input**
- 系统运行过程中产生的各类事件

**Process**
1. 实时接收并渲染事件
2. 区分展示：主智能体的判断 / 派出的子智能体 / 各子智能体的独立进度
3. 页面刷新后能恢复已有进度

**Output**
- 一个持续更新的过程视图

**验收标准**
1. **全程无"卡住不动"的黑盒期**（超过 10 秒无任何可见变化即视为缺陷）
2. **每个子智能体有独立的进度展示**，可分辨谁在干什么
3. 刷新页面后，**已有进度能恢复**，不从头开始
4. 能看出 F05 的拆解动作与 F06 的派兵动作

#### F12 · 会话持久化

| 项 | 内容 |
| --- | --- |
| 优先级 | P0 |
| 描述 | 会话状态持久保存，可中断后继续 |

**Input**
- 会话过程中的消息与状态

**Process**
1. 持续记录会话
2. 支持从记录中恢复

**Output**
- 可恢复的会话

**验收标准**
1. **服务进程重启后，之前的会话仍能继续**
2. 恢复后**上下文不丢失**（能接着之前的话题聊）
3. 恢复后**交付物仍在**

**边界与异常**
- 存储不可用时应有明确提示，不得静默丢失

#### F13 · 权限边界

| 项 | 内容 |
| --- | --- |
| 优先级 | P1 |
| 描述 | 建立并强制执行权限边界，且不可通过委派绕过 |

**Input**
- 系统配置的权限规则

**Process**
1. 对工具调用进行权限判定
2. 拒绝类规则对所有子智能体**强制继承**
3. 需要确认的操作挂起等待访客

**Output**
- 放行 / 拒绝 / 请求确认的判定结果

**验收标准**
1. **被禁止的能力，子智能体同样无法调用**（不得通过委派绕过）
2. 需要确认的操作**确实会挂起**，且在获得确认前不继续
3. 权限判定结果**在过程视图中可见**

### 4.6 扩展层

#### F14 · 自定义专精领域

| 项 | 内容 |
| --- | --- |
| 优先级 | P0 |
| 描述 | 访客可自助定义一个专精领域，系统随即具备该领域的处理能力 |

**Input**
- 访客对领域的自然语言描述（如"我想让它帮我做合同风险审查"）

**Process**
1. 主智能体根据描述**起草一份技能**（草稿状态）
2. 向访客展示草稿内容（领域用途、判断维度、处理步骤、交付模板）
3. 访客**确认或提出修改**；可迭代多轮
4. 通过确认后，技能上线
5. 之后命中该领域的输入，按新技能处理

**Output**
- 一份已上线的技能
- 一条对访客可见的"领域已创建"事件

**验收标准**
1. 访客**无需技术背景**即可完成一次自定义（由非作者测试者验证）
2. 未通过确认的草稿**不得上线**，不得影响现有领域
3. 自定义领域上线后，**该类输入确实走新领域处理**（可观察到的行为变化）
4. 自定义领域**只对创建者可见**，不影响其他访客
5. 全流程**不需要改动任何代码**

**边界与异常**
- 描述过于含糊 → 主智能体应先追问澄清，不得凭空发挥
- 与已有领域高度重叠 → 应提示访客并建议复用
- 草稿质量不达标 → 访客可放弃，草稿可删除
