---

## 1. 目标与背景

在已完成的「按库绑定向量模型」架构下，系统默认向量模型可自由切换，老知识库独立沿用旧模型。
本方案进一步解决**单知识库生命周期内的向量模型演进需求**：允许管理员/库所有者在知识库设置中，手动将已绑定的向量模型切换为新模型，并通过**全量索引重建机制**，确保已有文档在全新的特征空间内重新向量化，保持检索可用性与一致性。

---

## 2. 核心技术逻辑：为什么换模型必须重建？

1. **维度不兼容**：不同厂商或规格的向量模型输出维度不同（如 1536 维、1024 维、768 维等）。底层 PostgreSQL pgvector 的列类型 `vector(N)` 强校验维度，混用会导致数据库级执行异常。
2. **空间坐标不互通**：即便两个模型输出维度完全相同，高维语义坐标系亦毫无关联。用新模型计算的 Query 向量去对比老模型计算的 Chunk 向量，余弦距离等于随机噪音。
3. **零丢弃保障**：系统在文档首次入库时已将源文件（Markdown/TXT/PDF/Word/HTML）与切片文本持久化于磁盘和数据库。**重建索引只需重新触发向量化推理，无需用户重新上传文件。**

## 3. 用户路径与交互设计

```
[知识库设置 Tab]
       │
       ▼
[选择新向量模型] ── 点击「保存」
       │
       ├─► (该库文档数为 0) ──► 直接更新绑定 ──► 提示「保存成功」
       │
       └─► (该库文档数 > 0) ──► 拦截并弹出【二次确认弹窗】
                                       │
                     ┌─────────────────┴─────────────────┐
                     ▼                                   ▼
                 [取消]                              [确认更换并重建]
                   │                                     │
               保持原配置                           调用重建接口
                                                         │
                                             跳转至「文档」Tab 查看进度
```

### 3.1 前端交互细节
- **模型选择器**：位于知识库详情「设置」Tab，将当前的只读标签改为下拉选择框，展示系统可用向量模型列表，并标识出 `(系统默认)`。
- **高风险弹窗**：
  - **标题**：更换向量模型
  - **内容**：当前知识库已有 N 篇文档。更换向量模型需要重新生成全部文档的向量索引。重建期间知识库将暂停检索，是否确认更换？
  - **按钮**：取消（灰色默认） / 确认更换并重建（危险警示色）。
- **进度感知**：
  - 确认后自动切到「文档」Tab，库内文档统一变为「解析中/排队中」；
  - 复用现有的实时解析进度与切片计数器，完成后自动变为「已就绪」。

## 4. 状态流转与后端实现设计

### 4.1 核心状态机与流转步骤

```
                 POST /reindex
                       │
                       ▼
 ┌───────────────────────────────────────────────┐
 │ Step 1: 事务控制 (Atomic DB Mutation)          │
 │  - 校验新端点有效性并提取目标维度               │
 │  - 更新 advisor_knowledge_bases (新模型+新维度) │
 │  - 删除该库全部 embedding checkpoints 历史缓存   │
 │  - 将该库所有文档状态批量置为 'parsing'          │
 └───────────────────────┬───────────────────────┘
                         │
                         ▼
 ┌───────────────────────────────────────────────┐
 │ Step 2: 物理索引清理 (Storage Reset)          │
 │  - 清理 PgVectorStore 内存实例缓存             │
 │  - DROP TABLE 该库专属向量表 (彻底清除旧维度约束)│
 └───────────────────────┬───────────────────────┘
                         │
                         ▼
 ┌───────────────────────────────────────────────┐
 │ Step 3: 异步调度流水线 (Batch Ingest Pipeline)│
 │  - 遍历该库文档，提交至 Ingest 调度线程池       │
 │  - 读取磁盘源文档提取 Chunk 文本               │
 │  - 调用新绑定的 Embedding 模型生成新向量       │
 │  - 自动创建新维度向量表并持久化                 │
 │  - 更新文档状态为 'ready'                      │
 └───────────────────────────────────────────────┘
```

### 4.2 接口设计

- **路径**：`POST /api/advisor/knowledge/{libraryId}/reindex`
- **权限**：管理员 或 知识库拥有者（与库编辑权限对齐）
- **请求体**：
  ```json
  {
    "embeddingEndpointId": "model-endpoint-uuid"
  }
  ```
- **响应**：
  - 成功：`202 Accepted`，返回受影响文档数与目标模型信息。
  - 冲突：`409 Conflict`（例如已有文档正在进行初始上传解析尚未结束）。
  - 非法：`400 Bad Request`（端点不存在或模型非向量类型）。

## 5. 关键技术取舍与容灾边界

1. **原地重建（Drop & Recreate） vs 影子表（Shadow Table）**
   - **选择**：采用原地清空与批量重算机制。
   - **考量**：影子表虽能在重算期间保持旧模型只读检索，但需要维护两套实体表、双重调用配额和复杂的原子别名切换；本地知识库重算一般在几分钟内完成，原地重建逻辑链条最短、状态最清晰、零并发死锁风险。
2. **清理 Checkpoint 缓存的必要性**
   - `advisor_document_embedding_checkpoints` 默认按切片指纹缓存计算结果；若不主动清空该库的 checkpoint，重算流程会误将老模型的旧向量当作缓存命中写入新表，导致逻辑污染。
3. **服务异常中断保障**
   - 若重算期间应用意外重启，应用启动时的自愈逻辑会将停留在 `parsing` 的文档标为中断，并在后台调度重新消费或允许用户在界面上一键重试单篇文档。

---

## 6. 验收标准

1. **空库更换**：未导入文档的知识库更换向量模型，直接保存成功，数据库端点 ID 变更，不触发无谓的重算。
2. **有文档库更换**：弹窗正确提示受影响的文档数量，确认后各文档状态变为解析中，底层物理表维度更新。
3. **老数据完整度**：无需用户重复上传文件，已有文档的名称、正文、切片数量重算后保持完整。
4. **检索验证**：重算就绪后，在检索测试页输入问题，召回命中结果正常，无向量维度不匹配错误。
5. **门禁要求**：后端全量测试通过；前端单元测试通过，Lint 警告无新增，前端顺利 Build。
