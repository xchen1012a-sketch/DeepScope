以下七项已由作者拍板，是本方案的前提：

| 编号 | 决策点 | 结论 | 对方案的影响 |

## 2. 总体架构

### 2.1 架构形态

单体三段式，部署不变（单机、JDK 17 起）：

```
前端（Vite + React，按原型九菜单重建）
   │  HTTP/SSE（登录会话凭证）
后端（Spring Boot 单体 :18080，现有 backend 继续演进）
   ├─ 业务层（新增）：会话 / 技能 / 工具 / 知识库 / 设置 / RBAC 的接口与仓储
   └─ 智能体运行时（已有，继续使用）：
        HarnessAgent（工作区驱动）+ AG-UI 聊天接口 + 管理接口
   │
PostgreSQL + pgvector（业务数据与知识库向量，全系统一个库）
JSON 状态文件（框架 state store，智能体推理状态）
```

分工原则：

- **业务层**负责"页面要什么"：增删改查、列表过滤、按人隔离、事件时间线落库与回放。
- **智能体运行时**负责"任务怎么跑"：路由、拆解、派发、汇总，全部发生在工作区内，通过框架能力完成，业务层不重复实现。
- 两层通过"汇报动作协议"（第 3.1 节）衔接：运行时产生结构化事件，业务层落库并转发给前端。

### 2.2 保留与新建

| 现状 | 处理 |
| --- | --- |
| 后端：HarnessAgent 装配、工作区播种、AG-UI 接口、管理接口、登录 | **保留**，在其上扩展 |
| 后端：账号存 SQLite | **迁移**进 PostgreSQL |
| 后端：单智能体 + 单个事实调查员子智能体 + 行为文件 | **保留骨架**，行为文件按新文案重写（D6），三技能与更多子智能体在会话阶段播种 |
| 前端：登录、组件规范、i18n、HTTP 封装 | **保留**（登录接入新外壳） |
| 前端：旧控制台全部页面与路由 | **删除**（D1） |
| 前端：原型代码 | 作为九菜单页面的**蓝本**：页面结构、卡片形态、事件类型照搬；文案、模拟运行时不用 |

## 3. 核心机制设计（跨阶段共用）

### 3.1 汇报动作协议（D5 · 路线 A）

给主智能体注册一组**汇报动作**工具。主智能体在推理过程中调用它们"向外汇报"，每次调用产生一条结构化过程事件，经 SSE 通道下发前端，前端按事件类型渲染成原型卡片。SRS 中"过程必须可见"（P5）的所有验收点由此获得稳定数据源，不依赖对自由文本的猜测。

| 动作 | 对应 SRS | 产出事件 | 前端呈现 |
| --- | --- | --- | --- |
| 宣布路由 | F04 | route | 模式横幅："正在使用：〈领域名〉/ 通用模式"，含理由与备选 |
| 加载技能 | F04/P1 | load_skill | 技能加载卡片：文件路径、附带资源数 |
| 上报拆解 | F05 | decompose | 拆解卡片：子任务清单、各自执行方式（自办/派发）与理由；"无需拆解"时显示理由 |
| 派发登记 | F06 | dispatch | 派兵卡片：目标/关注点/上下文/交付格式四要素 |
| 自办登记 | F05/F06 | self_task | 自办卡片：主智能体亲自查的条目 |
| 上报事实 | F07 | subagent_facts / self facts | 事实条目：编号 + 事实 + 来源 + 结论 三段式 |
| 子智能体进展与落定 | F06 | subagent_progress / subagent_settled | 子智能体独立进度条；落定状态（完成/失败/超时/空） |
| 提交交付物 | F09 | deliverable | 交付物卡片：分节、条目、依据编号、冲突说明、推测标注 |
| 追问 | F02/F03/F10 | question | 提问气泡，本轮结束等待访客回复 |
| 提案新子智能体 | F08 | proposal → proposal_resolved | 提案卡片：原因、定义、可用工具；确认后"落盘生效"事件 |
| 权限裁决 | F13 | permission → permission_resolved | 权限卡片：谁、什么操作、命中规则；挂起等待访客裁决 |
| 过程说明 | P5 | advisor_note | 主智能体一两句说明气泡 |
| 技能起草与发布 | F14 | skill_draft → skill_published | 草稿卡片 → 发布确认 |

约定：

1. **事实三段式**是硬约束：编号（F1、F2…全局递增）+ 事实 + 来源 + 一句话结论；没有来源的条目不允许出现（写进行为文件与子智能体定义）。
2. **派发四要素**：每个子智能体收到的任务描述必须含 目标 / 关注点与边界 / 必要上下文 / 交付格式，且各不相同（F06 验收 1）。
3. 事件先落库（时间线表，含会话、轮次、序号），再推前端；前端刷新后先拉历史时间线再续订，实现 F11 的恢复。
4. 前端事件类型与原型 `domain/types.ts` 的 17 种事件一一对应，卡片组件可从原型移植。

### 3.2 一次任务的完整数据流转

以"仓库尽调"为例（F01）：

```
访客输入 ──→ 会话接口：落库访客消息（PostgreSQL）
        ──→ 主智能体开始推理（运行时）
             ├─ 宣布路由（route: 命中「仓库尽调」+理由）
             ├─ 加载技能（load_skill: skills/repo-diligence/）
             ├─ 上报拆解（decompose: 5 个维度，4 派发 1 自办，可并行标注）
             ├─ 派发登记（dispatch ×N）──→ 子智能体各自独立上下文执行
             │        └─ 子智能体用工具查一手信息，按三段式回传事实
             ├─ 事实回流（subagent_facts ×N，编号全局递增）
             │        └─ 失败/超时/空：重试一次或在交付物中显式说明缺失
             ├─ 自办登记（self_task：主智能体顺手查的部分）
             └─ 提交交付物（deliverable: 固定模板 + 依据编号 + 冲突说明）
        ──→ 事件逐条：PostgreSQL 时间线落库 + SSE 实时推送前端
        ──→ 交付物落库（含版本号，追问补充后版本 +1）
        ──→ 会话回到空闲，等待追问或新输入
```

追问（F10）：不重跑流程。主智能体基于已有上下文直接回答；需要新事实时才补派子智能体，新事实并入交付物、版本递增。

### 3.3 状态流转

| 对象 | 状态机 | 说明 |
| --- | --- | --- |
| 会话 | `idle → running → awaiting_visitor → idle`；任意态可 `→ failed` | running=推理执行中；awaiting_visitor=提案/权限挂起等待裁决；failed=不可恢复错误（会话内可见并说明） |
| 子智能体任务 | `queued → running → done \| failed \| timeout \| empty` | 失败/超时/空由主智能体感知并处理：重试一次或显式说明缺失，不静默丢失 |
| 技能 | `draft → published`；draft 可删除 | 未过访客确认的草稿**不得上线**（F14 验收 2） |
| 子智能体提案 | `pending → approved（落盘生效）\| rejected（退回通用能力）` | 未确认不得启用（F08 验收 2） |
| 权限判定 | `ask → granted \| denied` | ask 期间操作挂起，不继续执行（F13） |
| MCP 服务 | `connected \| error` | 连接失败记录原因，可重试；其工具须经审批后才可用 |
| 知识库文档 | `parsing → ready \| failed` | 解析失败记录原因，可删除重传 |
| 模型端点 | `enabled \| disabled`；全局唯一 active | 切换 active 即当前生效端点 |

### 3.4 按人隔离（D2）

- 所有自建资源（技能、会话、知识库、自定义工具、MCP 服务、模型端点、子智能体定义）记录**创建者**。
- 列表与详情接口默认按当前登录人过滤；**内置资源**（origin=builtin）对所有人可见、不可删除。
- **管理员**角色的列表接口可查看所有人的资源（带归属人列）。
- 技能生效侧走框架的按用户隔离能力（技能中间件支持按用户装配技能，F14 的"只对创建者可见"在运行时同样成立，而非仅页面过滤）。
- 会话同样按人隔离；管理员经管理视图查看全部（复用现有管理接口的会话清单）。

### 3.5 存储设计（D3）

| 数据 | 存储 | 说明 |
| --- | --- | --- |
| 智能体推理状态、会话消息上下文 | **JSON 状态文件**（框架 state store，不动） | 服务重启后可恢复续聊（F12）；符合 `.ai-spec`"状态存取必须走 state store 抽象" |
| 账号、角色、用户 | PostgreSQL | 账号从 SQLite 迁入 |
| 会话元数据（标题、状态、归属、时间） | PostgreSQL | 侧栏列表 |
| 事件时间线（全部过程事件，含轮次与序号） | PostgreSQL | 刷新/重启后回放过程（F11） |
| 交付物（结构化正文 + 依据清单 + 版本） | PostgreSQL | 追问并入后版本递增（F10） |
| 技能（元数据 + 说明文件正文 + 附带资源） | PostgreSQL + 工作区文件 | 元数据落库便于列表与隔离；生效文件落到按用户隔离的工作区技能目录 |
| 工具定义（名称 / 说明 / 入参 schema / 来源 / 执行绑定 / 权限）、MCP 服务配置（传输方式、命令或地址、密钥） | PostgreSQL | 运行时按关联接线到智能体；MCP 工具在注册审批后落库 |
| 知识库、文档、分块、向量 | PostgreSQL（pgvector） | 复用框架现成的 PG 向量存储实现；向量与业务数据同库，重启不重新计算嵌入 |
| 模型端点（含密钥） | PostgreSQL | 密钥仅服务端；接口只返回掩码（NF5） |
| 审计与配额用量 | PostgreSQL | 谁、何时、派了谁、改了什么（NF8）；token 配额核销（NF4） |

### 3.6 工具与 MCP 的分层（D7）

**工具是执行层**，也是模型能调用的最小单位。规范上就三样：`name`、`description`、`inputSchema`（JSON Schema，描述入参）。模型看到的是这份声明，据此决定调不调用、传什么参数。

**MCP 是协议层**：规定如何发现工具（`tools/list`）与调用工具（`tools/call`），本身不执行任何动作。一个 MCP 服务是一批工具的**来源**，不是与工具并列的另一类东西。

因此工具只维护**一份清单**，用「来源」区分执行绑定方式：

| 来源 | 执行绑定 | 需要额外填什么 |
| --- | --- | --- |
| 内置 builtin | 运行时自带 | 无 |
| 声明 declared | 宿主代码实现 | 无（只要 name / description / inputSchema） |
| HTTP http | 调用接口 | 服务地址（+ 路径与方法） |
| 脚本 script | 执行本地命令 | 命令与参数 |
| MCP mcp | 走协议调用 | 服务端连接信息，由 MCP 注册流程提供 |

两条实现约束：

1. **新建工具走导入，不手填参数。** 粘贴一段 OpenAPI 片段或一份 JSON Schema，平台据此生成工具：OpenAPI 里每个 operation 变成一个工具，path / query / requestBody 的字段直接翻成 `inputSchema.properties`，`required` 一并带过来；`servers[0].url` 作为默认服务地址。
2. **服务地址是选填的，它决定来源而不是能不能创建。** 填了 → 来源 HTTP，执行绑定为该地址；留空 → 来源声明，只落 name / description / inputSchema，执行交给宿主代码。若把地址设成必填，等于强行假设"每个工具都是一个 HTTP 接口"，与实际不符。

> 权限不在这张表里：权限是工具的**属性**（放行 / 需确认 / 拒绝），与来源正交，任何来源的工具都可以是三档之一。

## 4. 分阶段开发计划

每个菜单 = 一个完整阶段，阶段结束跑对应门禁（后端 `mvn test` + `spotless:check`；前端 `build` + `typecheck` + `lint`），通过才算完成。阶段顺序按依赖排定：

| 阶段 | 菜单 | 覆盖 SRS 功能 | 类型 |
| --- | --- | --- | --- |
| 1 | 开始 `/` + 工程地基 | 无（演示入口） | 地基 |
| 2 | 会话 `/chat` | F01–F07、F09–F12 | **核心** |
| 3 | 技能 `/skills` | F14 | 核心扩展 |
| 4 | 智能体 `/agent` | F08 + 原型新增（智能体编辑器） | 原型新增 |
| 5 | 工具 `/tools` | F13 + 原型新增（工具库、MCP） | 原型新增 |
| 6 | 知识库 `/knowledge` | 原型新增（RAG） | 原型新增 |
| 7 | 设置 `/settings` | 原型新增（模型端点）+ NF4/NF6 | 原型新增 |
| 8 | 用户与角色 `/access/users`、`/access/roles` | 原型新增（RBAC）+ NF8 | 原型新增 |

> 排序理由：会话是演示价值核心且依赖三技能播种，故技能**内容**并入阶段 2（技能**管理页面**才是阶段 3）；F08 依赖子智能体定义机制成熟，放阶段 4；知识库、设置、RBAC 相对独立，靠后。

### 阶段 1 · 开始页与工程地基

**目标**：新外壳可登录可导航；数据库与隔离基座就位，后续阶段不再动地基。

**前端**
- 移除旧控制台全部路由与页面（D1）；新建外壳：品牌区、九菜单导航（含分组折叠、移动端、语言切换）、"模拟数据"标识移除。
- 开始页：产品一句话定位（SRS 1.2）、"它能做什么"三条说明、三个示例输入入口（点击即跳转会话并预填）。
- 登录页保留并接入新外壳；登录后默认落开始页。

**后端**
- 引入 PostgreSQL（启用 pgvector 扩展）：建库与连接配置；账号从 SQLite 迁入（含引导管理员逻辑不变）；框架状态文件目录不变。
- 落"归属者"基座：当前登录人注入业务层，列表查询统一过滤（阶段 2 起直接使用）。
- 事件时间线与交付物的表结构在本阶段建好（会话阶段直接用）。

**数据流转**：登录 → 会话凭证 → 外壳按角色渲染菜单（权限点控制可见性，阶段 8 补后端强校验）。

**验收**：旧路由 404 或重定向到新外壳；登录/登出/语言切换可用；开始页示例入口可点击。

### 阶段 2 · 会话（核心）

**目标**：SRS 的 F01–F07、F09–F12 全部可演示、可验收。本阶段完成后作品的核心卖点成立。

**内容创作（D6，全部重写，不抄原型）**
- 三份技能说明文件：仓库尽调 / 方案设计 / 架构评审，各含领域用途、判断维度、处理步骤、交付模板、附带参考资料（F01/F02/F03 的 Process 与 Output 逐条对照 SRS）。
- 主智能体行为文件重写：路由（含"永不拒绝"与通用模式说明）、拆解纪律、派发四要素、依据标准、追问策略。
- 事实调查员等 2–3 个子智能体定义（三段式返回格式）。

**后端**
- 汇报动作协议落地（3.1 节全部动作），事件封装走 AG-UI 自定义事件通道；事件、交付物落库。
- 会话接口：会话列表（按人）、创建、改名、删除；对话走现有 AG-UI 接口；时间线查询（回放）。
- 三技能与子智能体播种进工作区；子智能体并行派发、失败重试/显式缺失按行为文件约束生效。
- 单任务 10 分钟与子智能体超时上限（NF1）、首反馈 3 秒（NF2：路由公告先行）、单会话 token 配额中止（NF4 骨架）。

**前端（照原型）**
- 侧栏：会话列表、新建、切换智能体（先只有主智能体）、模拟服务重启按钮（演示 F12）。
- 对话区：消息流、模式标识气泡、过程卡片（路由/加载技能/拆解/派兵/自办/事实/落定）、交付物卡片（分节+条目+依据编号展开+冲突与推测标注+版本）、追问建议。
- 挂起门：提案卡片（确认/拒绝）、权限卡片（允许/拒绝）、追问气泡；会话进入 awaiting_visitor 期间输入框引导相应操作。
- 刷新恢复：进入会话先拉时间线重建过程视图，再续订实时事件。

**数据流转**：见 3.2 节。**状态流转**：会话与子智能体状态机见 3.3 节。

**验收**：直接对应 SRS——F01（3 仓库 3 报告）、F02（3 需求 + 取舍理由 + 先提问）、F03（埋 3 缺陷全找出）、F04（路由正确 + 零拒绝）、F05（拆解随复杂度变化 + 理由可见）、F06（四要素各异 + 并行 + 重复执行派兵可不同 + 简单任务不派发）、F07（抽查结论 100% 可追溯且依据真实）、F09（同领域结构一致 + 冲突显式说明）、F10（不重跑 + 有记忆 + 会补查）、F11（无黑盒 + 独立进度 + 刷新恢复）、F12（重启后可继续、交付物仍在）。

### 阶段 3 · 技能

**目标**：F14 自定义专精领域全流程；技能资产管理。

**后端**
- 技能接口：列表（我的 + 内置；管理员可看全部人）、详情、新建（上传说明文件或现场起草）、编辑、发布、删除草稿。
- 发布 = 元数据落库 + 生效文件写入**按创建者隔离**的工作区技能目录，运行时对命中输入生效（3.4 节）；未发布不落生效目录。
- 会话内起草流：主智能体在对话中根据访客描述起草技能（skill_draft 事件）→ 访客确认/修改（可多轮）→ 发布（skill_published 事件）→ 后续命中输入走新领域。
- 与已有领域高度重叠时提示复用；描述含糊先追问（F14 边界）。

**前端（照原型）**：技能列表（状态徽章、来源内置/自建）、详情（领域用途/判断维度/处理步骤/交付模板、附带资源、"被哪些智能体使用"）、上传与起草入口、发布确认流。

**数据流转**：描述 → 起草（draft，落库）→ 确认 → published（写生效目录）→ 路由命中 → 会话走新领域。**状态流转**：`draft → published`，未过审不上线。

**验收**：SRS F14——非技术背景测试者可独立完成一次自定义；未过审不上线、不影响现有领域；上线后该类输入确实走新领域；只对创建者可见（另一账号看不到）；全流程不改代码。

### 阶段 4 · 智能体

**目标**：智能体查看与编辑器；F08 动态创建子智能体。

**后端**
- 智能体定义接口：列表、详情、编辑（行为、技能关联、工具关联、子智能体关联、知识库关联、工作区文件）。关联关系统一存智能体一侧（原型约定）。
- 行为编辑 = 主智能体工作区行为文件的在线编辑（带后果提示：影响所有会话）。
- 子智能体定义管理：从工作区目录读写（说明文件格式与现有格式一致）。
- F08：主智能体识别能力缺口 → 提案（proposal 挂起）→ 访客确认 → **新定义落盘到工作区子智能体目录** → 本次任务即可使用；拒绝则退回通用能力。

**前端（照原型）**：列表页（卡片）、详情编辑器六页签（行为 / 技能 / 工具 / 子智能体 / 知识库 / 工作区），多对多关联选择器；工作区页签做文件树 + 可编辑文件。

**状态流转**：提案 `pending → approved（落盘）| rejected`。

**验收**：SRS F08——至少成功触发一次（如尽调非 Java 项目自行创建对应调查子智能体）；创建必须经访客确认；新子智能体确实用于本次任务并产生结果。另：编辑后的行为/关联在下次会话生效。

### 阶段 5 · 工具

**目标**：F13 权限边界做实；工具库（执行层）与 MCP 服务（协议层）管理。

**概念依据**：工具与 MCP 的分层、工具定义字段与五种来源见 3.6 节；权限是工具属性，与来源正交。

**后端**
- 工具接口：列表、导入、编辑、删除。**不提供手填参数的新建入口**——工具从接口描述生成，或由 MCP 发现。
- 导入解析：OpenAPI 片段按 operation 展开（path / query / requestBody → `inputSchema`，`required` 一并带过来；`servers[0].url` 作为默认服务地址，可覆盖）；JSON Schema 按单工具解析。服务地址留空时落为"声明"来源，不绑定执行。
- 权限三档（放行 / 需确认 / 拒绝），判定接入框架权限引擎：**拒绝类规则对所有子智能体强制继承**（不得通过委派绕过，F13 验收 1）；"需确认"挂起 → 前端裁决 → 恢复执行；判定结果发 permission 事件（过程可见）。
- MCP 服务管理：注册（三种连接方式：本地命令 / SSE / HTTP；支持粘贴一行命令或一段配置自动识别）、连接测试、`tools/list` 拉取工具清单后**进入审批**——逐个确认权限（默认"需确认"）才落库为可用工具；密钥与环境变量仅服务端保存。
- 内置工具清单与权限默认值预置（读文件、执行只读命令、访问外部网络、查询包管理器元数据等）。

**前端（照原型）**
- 工具页分两层：上层是**工具表**（名称 / 来源 / 说明 / 入参 / 权限 / 操作），内置、声明、HTTP、脚本、MCP 来的工具同表呈现，来源用徽章区分，MCP 的徽章带服务名；下层是 **MCP 服务表**（服务名、传输方式、连接目标、贡献工具数），展开只列它贡献了哪些工具，不重复工具本身。
- 新建工具 = 导入对话框：选 OpenAPI 或 JSON Schema → 粘贴 → 展示识别出的 operation 列表（可勾选）→ 服务地址（可留空）→ 统一权限 → 导入。
- 添加 MCP = 两步：粘贴配置或命令识别连接信息 → 握手后列出发现的工具并逐个设权限 → 确认接入。
- 工具详情可查看交给模型的 JSON Schema 原文；已接入的 MCP 工具权限可随时改。
- 会话内权限裁决卡片（承接阶段 2 的门）。

**数据流转**：接口描述 → 解析生成工具定义落库 → 智能体运行时按关联装配可用工具 → 调用时先经权限判定（allow 直行 / ask 挂起等裁决 / deny 拒绝并告知原因）。MCP 链路：连接 → `tools/list` 发现 → 审批落库 → 调用走 `tools/call`。

**状态流转**：判定 `ask → granted \| denied`；MCP 服务 `connected \| error`；工具本身无中间态（导入即可用，可随时改权限或删除）。

**验收**：SRS F13——被禁止的能力子智能体同样无法调用（含委派场景）；ask 确实挂起且确认前不继续；判定在过程视图可见。工具导入：粘贴 OpenAPI 片段生成多个工具且入参正确（path / query / requestBody 三类都能翻出来）；服务地址留空得到"声明"来源工具；粘贴 JSON Schema 得到单工具。MCP：注册一个真实 MCP 服务后，其工具经审批出现在工具表中并可被主智能体调用；**未审批的工具不生效**。

### 阶段 6 · 知识库

**目标**：文档管理与检索测试台（原型新增功能，SRS 无对应编号）。

**后端**
- 知识库接口：建库（检索参数：分块大小、重叠、召回条数、相似度阈值）、文档上传（md/pdf/docx/txt/html）→ 解析 → 分块 → 向量化（用框架的读取器与嵌入模型；解析异步，状态 parsing → ready/failed）→ 向量入 pgvector 向量存储。
- 检索接口：按库检索，返回命中分块 + 分数；供检索测试台与智能体检索工具共用。
- 知识库与技能、智能体的关联（多对多，存智能体/技能一侧）。

**前端（照原型）**：列表页（库卡片）、详情页（文档表格：状态徽章/大小/时间；上传；删除）、检索测试台（输入 → 命中列表带分数与高亮）、检索参数编辑。

**数据流转**：上传 → 解析分块（状态可见）→ 向量化入库 → 检索打分 → 命中高亮；智能体/技能引用后，调查类子智能体可检索取证（依据来源含知识库命中）。

**状态流转**：文档 `parsing → ready | failed`（失败记录原因，可重传）。

**验收**：五种格式各传一份可到 ready；检索测试台分数与高亮正确；解析失败有明确原因；重启后分块与向量可直接检索（不重新嵌入）。

### 阶段 7 · 设置

**目标**：模型端点管理；配额与限流参数。分两个里程碑（D4）。

**里程碑一：端点管理 + 重启生效**
- 端点接口：两类（大模型 / 向量模型）× 多服务商（OpenAI 协议 / Anthropic / DashScope / 自定义）的增删改查；密钥仅服务端存储，界面只显掩码；全局唯一"当前端点"，切换后**重启生效**（写配置，启动时装配对应模型）。
- 大模型端点供智能体；向量模型端点供知识库嵌入。
- 配额与限流参数：单会话 token 上限、单账号日任务配额、入口限流阈值（NF4/NF6）。

**里程碑二：热切换（不重启）**
- 模型装配从"启动时静态装配"改为"按当前端点动态构造"：切换当前端点后，下一次会话即用新模型，无需重启服务。

**前端（照原型）**：端点列表（类型/服务商/掩码/启用态/当前标记）、新建编辑表单、切换当前端点确认框、配额参数表单。

**验收**：里程碑一——新增端点、切换、重启后生效，密钥前端不可见；里程碑二——切换端点后新会话立即使用新模型，全程不重启。配额超限任务被中止并说明（NF4）。

### 阶段 8 · 用户与角色

**目标**：RBAC 管理做实（D8）；权限点前后端双重生效。

**后端**
- 角色接口：角色的增删改查、权限点集合编辑、启用停用；内置角色不可删除不可改权限。
- 用户接口：用户的增删改查、角色分配、启用停用（停用即无法登录，在途会话失效）。
- 权限点按原型九个：会话使用 / 智能体查看 / 智能体管理 / 技能管理 / 工具管理 / 知识库查看 / 知识库管理 / 设置管理 / 权限管理。后端接口按权限点强校验（此前阶段仅菜单可见性）。
- 管理员视图：管理员在各管理页可查看**所有人**的自建资源（D2），带归属人列。
- 审计日志：登录、权限变更、资源发布/删除、提案与权限裁决（NF8）。

**前端（照原型）**：角色页（权限点矩阵勾选、内置角色锁）、用户页（角色分配、状态切换）。

**验收**：无对应权限点的账号，菜单不显示**且**接口拒绝（双重校验）；内置角色不可改；停用用户立即不可登录；管理员可见所有人的技能/会话/知识库（D2 验收）。
