## 1. 要解决的问题

技术参谋现在的手脚是随智能体一起长出来的内置能力。下一步要让人接进外部能力：从接口描述导入，或接上一个 MCP 服务再选用它提供的工具。

若接上之后所有智能体都能看见全部工具，模型会在一堆无关能力里乱选。所以外部能力必须先进入统一清单，再由每个智能体事先圈定自己能用哪些。

## 2. 已经定死的前提

这些在总方案里已经拍板，本文沿用，不再改口：

- 工具是可以被调用的最小动作。MCP 只负责发现和转发，自己不是另一套清单。
- 全系统只有一份工具清单。用来源区分内置、声明、接口、脚本、MCP。
- 新建工具只能靠导入接口描述或结构描述，不能手填参数。地址可以空着；空着就只保留声明，先不执行。 todo 地址空的也可以执行，如果硬性绑定服务器地址会限制
- 权限是每件工具自己的属性，分放行、需确认、拒绝，和来源无关。
- 拒绝必须连子智能体一起生效，不能靠派发绕开。需确认的调用要停住，访客点头之前不继续。
- 自建的工具和 MCP 服务只对创建者和管理员可见。内置工具所有人可见，只有管理员能改。
- 密钥只留在服务端。页面上看不见原文。不把访客写来的程序放在本机上执行。



## 3. 总体思路

四块记录，一条方向：

MCP 服务负责“怎么连”。工具清单负责“有哪些可被考虑的动作，以及各自的权限”。智能体负责“我这次可以用其中哪些”。权限门负责“这一次调用放不放行”。

模型、会话过程和子智能体都只看见智能体已经圈定、并且已经批准的工具。它们不直接保存 MCP 的地址或密钥。

框架里已经有最后一跳：能按本地命令、长连接或普通接口连上 MCP 服务，问出工具，再把调用转回去。这一跳继续用。本阶段补的是它前面的登记、审批、智能体圈定，以及把清单上的权限送进框架已有的判定。

不采用另外两种接法。连上就整包注册、调用时再拦，模型仍然看得到未批准的工具。MCP 单独做一套清单，页面、权限和智能体引用都要做两遍。

## 4. 四块记录怎么互相指

**MCP 服务**记下服务名称、传输方式（本地命令、长连接、普通接口）、连接目标、密钥和环境变量、创建者、连通或出错。它自己不能被模型调用。密钥不复制到工具上，也不写进智能体工作区。

**工具**记下名称、说明、入参样子、来源、执行办法、权限、创建者。来源是 MCP 的工具只记住自己属于哪个服务，不记住连接细节。一件工具只属于一个服务。一个服务可以贡献多件工具。来源是接口的工具记住地址、路径和方法。来源是声明的工具只有名称、说明和入参样子。内置工具对应运行时自带的能力。

**智能体的选用**只做一件事：选用清单里的哪些工具。不单独再绑一次协议。工具在诞生时已经带着自己的调用方式。来自 MCP 的，天生记得自己属于哪个服务；来自接口导入的，天生记得自己的地址。智能体勾到某件工具，调用方式跟着走。

为了少点很多次，同一个 MCP 服务下的工具在选用界面上收成一组，可以整组勾上。这是一次勾选多件工具，不是第二遍绑定。

**会话里的判定**记下这一次是放行、拒绝还是在等访客。需确认被允许或拒绝之后，再补上裁决结果。过程视图靠这条记录渲染，不靠猜测模型说了什么。

引用方向可以收成一句：工具诞生时就带好调用方式，进入清单；智能体只选用工具；运行时装配被选用且已批准的那些；调用时再过权限门。

## 5. 两道门

两道门解决的是不同的事，缺一不可。

**第一道在工具上：批准。** MCP 连上后问到的工具，先是待审，不能调用。人逐件决定是否收进清单，并设定权限。默认是需确认。没批准的不进清单，任何智能体都用不了。

**第二道在智能体上：选用工具。** 批准只表示这件工具有资格被选用，不表示每个智能体都能用。每个智能体事先从清单里勾选自己能用的工具。没勾的，一件都带不上，无论它来自 MCP 还是来自接口导入。

人不需要判断“这件工具支不支持 MCP”，也不需要再去绑一次协议。这个信息在工具创建时已经写死，清单上用来源和所属服务标出来。勾选它，就等于把它连同调用方式一起交给这位智能体。

同一个服务下的工具可以整组勾选，省得一件件点。整组勾选之后，运行时带上的是该组里已经批准的工具。后来服务里新出现的工具仍要先批准；批准后，已经整组勾选该服务的智能体在下一轮会自动带上它。若只勾了该组里的几件，新工具不会自动加进来。

内置能力仍是这位智能体自己的基本手脚，不靠这次勾选，但调用时同样过权限门。内置工具的默认权限在本阶段预先放好：读文件、只读命令、查包信息这类偏只读的默认放行；会改东西或访问外网的默认需确认。管理员可以改。

## 6. 运行时怎么装配

每一轮开始时，按“这一轮实际回答的那位智能体”装配，而不是按账号装配。锁定模式用会话绑定的那位。自由模式先分派，再按分派到的那位装配。

装配只看这位智能体勾了哪些工具，再按每件工具诞生时带上的调用方式去接：

1. 内置能力始终在，不靠勾选。
2. 勾了来自 MCP 的工具，且所属服务连通，调用就走回那个服务。服务出错或已删除，这件工具本轮不出现。
3. 勾了来自接口导入的工具，有地址就发请求。只声明、没有执行办法的，不挂成可调用工具，避免模型以为自己能执行。

未批准的工具不会出现在这一轮的可见集合里。智能体工作区里的文件不能自行把某件 MCP 工具加回来，否则第二道门会被绕开。

装配发生在每一轮开始，不用重启进程。改勾选、改权限、批准新工具，都从下一轮生效。已经跑到一半的那一轮仍用开始时的那一套。

## 7. 调用时的权限

权限门拦在“模型决定调用”和“真正执行”之间。清单上的三档是权威，框架里已有的判定负责执行这个权威。MCP 工具在框架里原本会每次都征求确认；本阶段用清单上的档位覆盖这一个默认，否则人设成放行也不会生效。

- **放行**：直接执行。MCP 来的就转给所属服务，接口来的就发请求，内置的就走原有能力。
- **拒绝**：不执行。把原因退回给模型，并在会话过程里记一笔拒绝。同一轮里模型不能靠换一种说法再执行它。
- **需确认**：整轮停住，状态与提案等待访客相同。访客看到是哪件工具、准备用什么参数、为什么要确认。点头只放行这一次调用，然后本轮继续。拒绝则按上面的拒绝处理。确认之前，这一轮不继续往下做。

同一时刻一轮只挂起一个确认。模型若还想调别的，等这一次有了结果再说。

判定结果进入会话过程，刷新之后仍在。

## 8. 子智能体不能绕过

派发子智能体时，子智能体的工具集合是主智能体这一轮可见集合的子集，再过一遍拒绝。主智能体被拒绝的能力，不能写进子智能体的定义里重新打开，也不能在派发时临时加上。

需确认不会因为派发就变成放行。子智能体撞上需确认，同样把整轮停住，由访客裁决。访客面对的仍是这一次具体调用。

子智能体自己提出新能力时，走的仍是阶段四的提案：人批准后定义才落盘。那条路径不能用来偷偷启用一件被拒绝的工具。

## 9. 导入如何进入同一条链

导入不产生第二份清单。

粘贴接口描述时，里面每个操作变成一件工具。路径上的参数、查询参数、请求体都收进这件工具的入参样子，必填一并保留。描述里若带了服务地址，就作为默认地址，导入时可以改。填了地址，来源是接口，调用时向该地址发请求。地址留空，来源是声明，只保留声明，不绑定执行，智能体也不能把它当成可调用工具。

粘贴一份结构描述时，只生成一件工具，规则同上。

导入时人选定一个统一的权限档，默认需确认。导入完成即可出现在清单里，但要在某个智能体上点名之后，那位智能体才会在下一轮看见。

脚本这一来源留在模型里，本阶段不提供“写一条命令就变成工具”的入口。这是为了守住“不在本机执行访客提供的程序”。

## 10. 服务的一生

**登记。** 人粘贴一行命令或一段配置，系统认出是本地命令、长连接还是普通接口。先保存服务并试连。连不上就记为出错，并记下原因，不产生工具。连上之后列出待审工具，人逐件批准并设权限，批准的才进清单。

**重新拉取。** 可以再次询问服务现在有哪些工具。新出现的仍是待审。服务里已经消失的，清单里对应项立即不可用，智能体下一轮不再看见。说明或入参变了，下一轮模型看到的是新样子。已经勾选该服务的智能体，会在下一轮带上新批准的工具。

**出错。** 调用或拉取失败时，服务变为出错并记下原因。它贡献的工具本轮不可用，调用按失败退回，不改走别的执行办法。人可以再试连。

**删除。** 删掉服务时，它贡献的工具一起从清单失效，智能体上对这个服务的勾选一起去掉。密钥随之删除。

**改权限。** 已进清单的工具可以随时改档。下一轮按新档判定。进行中的那一轮不受影响。

## 11. 人在页面上做什么

工具页分上下两层，不把同一件工具画两次。

上层是工具表：名称、来源、说明、入参、权限、操作。五种来源同一张表，用来源徽章区分。MCP 来的徽章带上服务名。可以改权限、看交给模型的入参原文、删除。没有手填参数的新建按钮。新建就是导入：选择接口描述或结构描述，粘贴，勾选识别出的操作，地址可留空，设一个统一权限，然后导入。

下层是 MCP 服务表：服务名、传输方式、连接目标、它贡献了多少已批准工具、连通还是出错。展开后只列出它贡献的工具名字，详细编辑仍回到上层工具表。添加服务是两步：先认出连接信息并试连，再逐件设权限并确认接入。

智能体编辑页的工具页签是同一份勾选清单，不再分成“先绑工具、再绑协议”。MCP 来的工具按所属服务收成一组，可整组勾，也可只勾其中几件。接口导入的工具按件出现在同一张清单里。没勾选时外部工具是空的，并写明这位智能体不会使用它们。内置能力单独列出来，供查看和改权限，不放进勾选里冒充外部工具。

会话里需确认时出现裁决卡片。点头或拒绝之后，过程里留下判定结果。

## 12. 谁能看见

自建工具和 MCP 服务只对创建者和管理员可见、可改。另一位普通用户看不见，也不能把别人的服务勾到自己的智能体上。

内置工具所有人可见。只有管理员能改它们的权限。

管理员在工具页能看到所有人的自建项，并带上归属。密钥对任何人的页面都只显示掩码。

本阶段先按“是不是管理员、是不是创建者”来守这些接口。细到“工具管理”这个权限点的角色矩阵，留到用户与角色那一阶段；到那时同一批接口补上权限点校验，不改这里的归属规则。

## 13. 本阶段明确不做

- 不手填参数来新建工具。
- 不把脚本来源做成可创建的执行入口。
- 不把未批准的 MCP 工具注册给模型。
- 不让未勾选的智能体使用任何 MCP 或导入工具。
- 不在页面或工作区保存密钥原文。
- 不在本阶段做知识库检索工具。检索要等知识库阶段。
- 不在本阶段做角色矩阵。只守住创建者和管理员。



## 14. 怎样算做对

- 粘贴一段含路径参数、查询参数和请求体的接口描述，能生成多件工具，入参和必填正确。地址留空的是声明，不能被调用。一份结构描述只生成一件工具。
- 登记一个真实 MCP 服务后，未批准的工具不会被任何智能体用到。批准后，只有勾选了这些工具的智能体能在下一轮用到，并且调用确实回到那个服务。不用再单独绑定一次协议。
- 没勾选这些工具的智能体，看不到它们。
- 把一件工具设为拒绝后，主智能体调不了，它派出去的子智能体也调不了。
- 设为需确认的调用会停住，确认前这一轮不继续。确认或拒绝之后，过程视图里看得到判定。
- 服务删掉或处于出错时，相关工具不再被调用，也不会偷偷换成别的执行办法。
- 另一账号看不到别人的自建工具和服务。密钥不出现在页面上。



## 15. 请你重点看的一个推论

智能体只选用工具，不第二次绑定协议。协议在工具创建时已经钉死。

整组勾选某个 MCP 服务时，该服务里后来新批准的工具，会自动进入所有整组勾选了它的智能体。只勾了其中几件的，新工具不会自动加进来。
