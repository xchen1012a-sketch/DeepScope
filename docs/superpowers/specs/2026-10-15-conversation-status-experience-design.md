# 会话执行体验优化方案：动作说明、结果展示与运行律动

日期：2026-10-15（Asia/Shanghai）\
状态：供用户审查。本次只检索与设计，未修改功能代码、未重启服务、未启动浏览器。

## 1. 推荐方向

将会话中的工具展示改成“可读的执行过程”：主界面说明正在做什么、有哪些实际进展；执行命令、输入参数和原始输出放在按需查看的详情里。

保留已经做好的批次折叠、整轮折叠与真实耗时，但重新设计每条记录承载的信息。单纯把长命令收起来，仍不能解决“看不懂执行过程”的问题。

推荐最终体验：**一条清晰的当前状态、一组紧凑的步骤摘要、随时可查的真实结果。运行时有轻柔律动，结束时停止，异常时明确提示。**

## 2. 参考依据与项目事实

### 官方资料支持的原则

OpenAI的[延迟优化指南](https://developers.openai.com/api/docs/guides/latency-optimization#make-your-users-wait-less)建议展示真实步骤，并提供加载反馈，让用户能观察到进展。本文据此设计运行状态，不用虚假的进度百分比营造进展。

[ChatGPT扩展UI指引](https://developers.openai.com/plugins/concepts/ui-guidelines)强调轻量的会话内展示、按需显示更多内容，以及避免重复表达。本文采用这种信息层级，不把工程日志铺成主对话。

[官方UI参考](https://developers.openai.com/plugins/reference#windowopenai-component-bridge)分别定义工具输入、工具输出及结果元数据。这能支持“输入与结果分开”的设计，但不是ChatGPT所有内置工具界面的完整规格。

**官方公开资料没有给出当前ChatGPT每一种状态文案、思考栏样式和律动的完整参数。以下布局、文案和动效均是适配本项目的建议，不声称为官方逐像素复刻。** 本次通过网页检索获取公开资料，没有打开用户浏览器或操作ChatGPT页面。

## 3. 主界面先展示“动作”，不直接展示命令

每个步骤主要回答三个问题：做什么、处理什么对象、目前是什么状态。标题使用简短自然语言，命令、长路径、JSON不占据默认位置。

以下是拟采用的文案示例，不代表当前实际执行结果：

| 操作类型 | 执行时 | 返回后的主界面 |
|---|---|---|
| 读取文件 | 正在读取 TurnGroup.tsx | 已读取 TurnGroup.tsx |
| 搜索源码 | 正在搜索会话调用位置 | 已返回搜索结果 |
| 可明确识别的测试操作 | 正在运行会话测试 | 测试已结束；有可信测试报告时再显示通过/失败数量 |
| 无法可靠识别用途的终端操作 | 正在执行本地操作 | 本地操作已结束 |
| 派发子任务 | 正在派发前端审查任务 | 已派发，等待任务结果 |
| 子任务实际结束 | 等待审查结果 | 对应审查任务已返回 |

标题优先使用与该步骤关联的公开任务说明，其次使用工具动作与可辨识对象，最后使用中性动作名称。文件默认显示文件名；需要区分同名文件时再显示短相对路径。

不能仅看到`execute`或一段包含“test”的命令，就编造“正在验证全部测试”。复合命令、未知脚本无法确定用途时，使用中性标题。工具返回结束也不能自动写成“任务成功”。

对思考中的状态，主界面采用“正在分析”“正在生成回复”等有事件依据的短状态。已有思考记录留在过程详情，不继续用不断变化的内部英文片段充当面向用户的主要进度说明。模型正常输出的公开说明文字仍按原顺序保留。

## 4. 点击后先看结果，输入参数放到技术详情

每个步骤的默认详情先展示执行结果，而不是先把参数JSON展开。

推荐详情顺序：

1. **结果摘要**：实际返回了什么，或者为什么失败。
2. **结果内容**：匹配类型的可读展示，例如文件片段、搜索命中、测试报告、子任务摘要。
3. **技术详情**：实际工具名称、完整命令、输入参数、原始输出与准确耗时，按需查看。

点击步骤时，优先复用现有“执行过程”侧栏定位到该步骤，避免在聊天正文里连续嵌套参数、日志和多层滚动框。批次只负责展开步骤列表，步骤详情集中在一处查看。

| 返回情况 | 推荐处理 |
|---|---|
| 测试报告包含可信统计 | 显示实际通过与失败数；完整日志放技术详情 |
| 搜索工具返回命中项 | 显示实际命中数量与简短条目，可查看原文 |
| 读取文件 | 显示文件名与返回片段，长内容按需查看 |
| 工具正常结束但没有可展示输出 | 显示“操作已结束，未返回可展示内容” |
| 工具尚未返回 | 显示“等待结果”，不能用输入参数填充结果区 |
| 原始返回本身只是参数回显 | 保留在原始输出，不包装成已获得业务结果 |
| 失败或拒绝 | 先显示简短原因，错误栈和技术日志留在详情 |

“发现3个问题”“测试全部通过”等结论必须有实际结果支持。工具仅返回退出码时，只能描述命令执行状态，不能替用户认定目标已经完成。

## 5. 批次标题也要能读懂，数量作为补充

保留连续操作折叠，但主标题从“6项操作”提升为能理解的动作摘要，例如：

> 检查会话相关文件 · 4项操作 · 执行中 ›

如果没有可信的阶段说明，则用动作类别组合，例如“读取文件与检索内容 · 4项操作”，不臆造这些调用的业务目的。

- 默认收起密集操作，展开后是步骤标题与各自状态，不直接露出完整命令和参数。
- 说明文字、思考和需要用户处理的卡片仍然作为分界，不把不同上下文硬合在一起。
- 有失败时，收起状态仍显示失败数量；是否继续、是否等待确认保持可见。
- 新结果到达时不强制展开，不覆盖用户的开合选择。
- 时间线定位依然会展开并定位对应步骤，不因展示优化失去可追溯性。

派发需要单独说清：“工具调用返回”可能只说明派发成功；只有收到子任务实际完成事件，才能显示该任务已返回。不能拿派发记录的done状态充当审查完成。

## 6. 运行律动：柔和、集中，并与真实状态同步

建议采用**文字轻微流光 + 小状态点呼吸**的组合。浅灰标题上有一条很淡的亮度变化，状态点缓慢呼吸；文字和行的位置保持稳定，不跳动、不改变宽度。

下列参数是本项目建议值，不是官方参数：文字流光约1.8–2.4秒一轮，状态点约1.5–2秒一轮，状态切换约150–200ms淡入淡出。

| 状态 | 文案与动效 |
|---|---|
| 已接收、等待开始 | “已接收，等待开始”，低强度等待反馈 |
| 思考或工具执行中 | 当前步骤标题柔和流光，配一个呼吸状态点 |
| 多个操作并行 | 批次标题维持主要律动；展开的各行用静态状态标记，避免一屏多个转圈 |
| 等待子任务或工具返回 | 明确显示“等待结果”；只有可确认的活跃状态才维持等待反馈 |
| 等待用户确认 | 停止运行律动，突出需要确认的事项 |
| 正常结束 | 停止律动，切换静态文字与可用结果 |
| 失败、取消或断连 | 停止律动，显示对应原因或连接状态，不继续装作正在工作 |
| 达到执行上限但产生总结 | 停止律动，保留上限提示，不包装成普通成功 |

同一可见区域只保留一个主要动画焦点；批次展开后也不让所有工具行同时闪动。用户选择系统“减少动态效果”时，关闭流光与呼吸，用静态状态标记代替。

没有真实进度比例时不显示百分比。等待时间变长可以展示实际已等待时长，但不能自动声称“马上完成”，也不能仅凭时间长就认定工具已经超时。

状态变化用可读文字表达，不仅依靠颜色和动画。辅助阅读只在步骤或状态切换时提示，不随动画、计时每秒重复播报。

## 7. 一轮会话如何呈现

以下是展示示意，具体标题、数字和状态都需要由真实数据提供。

执行中：

> 我先检查会话展示和工具结果的处理方式。
>
> ◌ 正在读取会话相关文件 · 4项操作 ›
>
> 已读取配置，接下来检查实际返回内容。
>
> ◌ 正在检查工具返回 · 3项操作 ›

展开某批次后：

> 已读取 TurnGroup.tsx · 查看结果
>
> 已返回调用位置的搜索结果 · 查看结果
>
> 正在执行本地操作 · 查看当前输出

运行结束后：

> 用时 1分钟 22秒 ›
>
> 最终回答与交付结果……

最终整轮折叠仍然保留。过程有异常或达到上限时，提示不能随着折叠消失；历史数据只能计算总时长时仍明确标“总用时”，不混淆两种时间口径。

## 8. 与当前项目的衔接

复用现有工具行、批次、思考状态、执行过程侧栏和运行事件。先改变展示层级与反馈，再补足有实际依据的动作标题和结果摘要，不另建会话引擎。

建议分两步完成同一套目标体验：

- **第一步：完成展示与律动。** 主行不再拼长命令，详情优先结果；当前状态使用统一的柔和动效，等待确认、完成和失败时正确停止；保留现有折叠与定位。
- **第二步：补足有意义的摘要。** 利用现有公开任务说明、工具类型和结构化结果，完善动作标题、测试/搜索结果和子任务进度；缺数据时中性降级，不额外为每个标题调用一次模型。

两步都是本次整体方案的组成部分，不能只加动画就把“全面优化”算作完成。当前工具结果类型与任务说明的覆盖程度需在实施时逐项验证；本方案没有把拟新增的摘要能力写成已有能力。

## 9. 验收时重点检查

1. 未展开技术详情时，主对话不出现长shell命令、绝对工作目录或原始参数JSON。
2. 能读懂当前在进行什么操作；无可靠用途信息时使用中性标题，不猜业务目的。
3. 打开步骤先看到实际结果或等待状态；参数与结果明确分开，空结果不回退为参数。
4. 动效只跟随真实运行状态；完成、错误、取消、待确认后及时停止；减少动态效果设置有效。
5. 密集派发不会铺满屏幕，折叠摘要保留正在执行和失败信息；派发成功不等于子任务完成。
6. 更新、刷新、整轮开合和时间线定位不破坏已有顺序与批次开合行为；展开时阅读位置稳定。
7. 真实会话含复合命令、空返回、错误、子任务和上限总结时，都有正确展示，不能只用理想模拟数据验收。
8. 没有结果证据时，不出现“发现若干问题”“全部通过”“任务成功”等推测结论。
