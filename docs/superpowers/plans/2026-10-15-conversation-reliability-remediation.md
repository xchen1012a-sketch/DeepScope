# 会话模块稳定性修复技术方案

> **For agentic workers:** 用户批准后，使用 superpowers:executing-plans 按阶段在当前任务执行；不自动委派、不自动提交。实施步骤使用复选框跟踪。

**Goal:** 修复运行中输出被覆盖、停止失效、确认无法恢复及保存/回放不一致，覆盖本次审查确认的13项问题。

**Architecture:** 复用现有运行store、AG-UI运行与恢复协议、服务端兜底保存和时间线。统一运行身份、终态与保存归属，先修执行链路，再修数据与展示；不重建会话引擎。

**Tech Stack:** 当前项目的React、TypeScript、TanStack Query、Vitest；Java、Reactor、Spring MVC SSE、Maven及现有数据库。

**Spec:** 本文第1—7节为修复设计与契约，第8—10节为实施、验证和回滚计划。本文是待审查方案，尚未实施。

日期：2026-10-15。范围以本次核对的工作区源码为准；已有混合修改和其他任务的并发改动必须保留。

## Global Constraints

- 不修改用户原始消息、历史正文、真实耗时或工具原始返回，不用猜测补齐结果。
- 不新增消息队列、事件总线、模型摘要调用或独立运行引擎。
- 沿用现有AG-UI中断/恢复协议，不自造另一种工具确认协议。
- 默认不启动浏览器，不发送真实模型请求；运行状态用受控流和并发测试验证，视觉验收单独记录。
- 所有新增界面文案同步en、zh-CN词典；用户可见行为同步docs/v2中英文文档。
- 不自动commit、push或重启服务；运行中的用户任务不能为了验证被中断。
- 涉及取消与恢复的框架语义，按`.ai-spec/change-levels.md`的高级改动执行；本方案审查通过后才进入业务代码实施。

## 2. 技术决策

推荐采用“现有链路内统一运行归属”的方案：保留现有架构，为异步更新、取消、确认和保存建立一致的归属约束。

不采用仅补前端判断的方案：它无法解决服务端先取消后鉴权、初始化取消及兜底保存竞争。不在本轮引入持久化任务中心或完整断线续传系统：这些属于另一个架构目标，不能以此扩大本次13项修复。

核心规则如下：

1. 一次运行只修改自己的状态，旧回调不能写新运行。
2. 新请求不能隐式取消现有运行；取消必须来自明确操作。
3. 停止是执行生命周期的一部分，初始化、订阅和资源释放均遵守同一取消标记。
4. 等待确认是独立状态，普通发送和自动出队都不能代替确认。
5. 流结束、回复保存成功、会话允许执行下一条，是三个不同节点。
6. 同一runId最多产生一份最终保存记录，兜底与前端提交共享去重边界。

## 3. 阶段一：运行隔离、取消和断流

### 3.1 前端运行身份与异步隔离：C01

沿用现有本地`runInstanceId`与协议`runId`，不再使用会随模型步骤变化的`startedAt`判断运行归属。

- 本地实例标识在开始发送时生成；协议runId在发起AG-UI请求前确定，供取消、确认和保存对账。
- 访客消息保存、路由、流信号、异常、缓存刷新后的收尾、自动出队及定时回调，全部携带捕获的实例标识。
- 状态更新在实际写入store时再次比较身份；不能仅在某个await之前检查一次。
- 释放controller、运行句柄及租约时使用比较后删除，旧运行不能删除新运行的资源。
- 输出结束后进入“收尾中”，停止运行律动；保存/缓存对账未结束时，新输入可以排队，但不开始第二个执行实例。
- 不依赖“延迟50毫秒”保证顺序。下一条由当前实例完成收尾后原子领取，领取前重新检查实例和状态。

### 3.2 服务端准入与资源准备：C02、C03

改造顺序为：身份与权限校验 → 原子占用会话运行槽 → 技能/智能体/租约准备 → 订阅流。以下是拟调整的内部边界，不能当作项目当前已经存在的独立API。

- 将现有resolver中的所有权、智能体可见性/绑定和额度检查，与技能同步、租约获取分开；复用现有检查实现，不能复制出两套不同授权规则。
- 权限校验通过后使用现有ActiveRun容器原子登记。已有运行时返回冲突，不调用`cancelActiveRun`替换它。
- 在运行槽登记后执行耗时准备。框架处理器需支持复用已校验上下文，并提供准备/清理边界；若需新增扩展点，采用可选、默认无操作的方式接入自动配置，旧入口保留，不让框架依赖应用SessionStore。
- ActiveRun记录初始化、活动、停止和结束阶段。取消标记必须先写入，再处理当下已经创建的句柄。
- 初始化任务返回时、发布ProcessResult时、订阅前都检查取消标记；晚到的句柄立即清理，不再调用模型或执行工具。
- 清理幂等。正常结束、异常、超时、显式停止和初始化失败只能释放本次运行的锁与资源一次。
- ToolRuntimeCoordinator的租约归属需加入runId比较，避免旧运行晚到的释放操作影响新运行；保留现有调用方式的兼容入口，应用新路径使用带身份的入口。

### 3.3 SSE结束判定与局部过程保留：C08、C09

- `runAdvisorStream`记录是否收到本次运行的明确终态。EOF本身不等于正常完成。
- 收到RUN_ERROR保留错误语义；如果配置随后补发RUN_FINISHED，不得覆盖为成功。
- 没有可信终态的EOF标记为连接中断，保留部分正文、分析和工具过程，展示可理解提示。不能仅因流短就补一个成功结果。
- 用户主动停止显示“已停止”，不误报为网络异常。
- 残留判定包含非空分析、有内容的parts及尚未对账的工具过程；不能仅检查正文和liveEvents。
- 服务端中断保存完成后再进行一次有归属校验的详情对账。若请求失败，保留本地快照，不能提前删掉最后一份过程。

## 4. 阶段二：确认恢复与队列

### 4.1 工具确认恢复：C04

使用已有`RunFinished.outcome.interrupts[]`和`RunAgentInput.resume`，复用`AguiResume`，不把业务“创建子智能体提案”当作工具权限确认。

- 解析并保存完整中断标识、原因、工具身份、响应schema及必要展示信息，和原runId关联。
- ConversationPanel在遇到工具确认时显示独立确认卡片；显示允许用户核对的动作和参数，提供批准、拒绝、取消等待。现有ProposalCard继续处理业务提案。
- 批准与拒绝均使用`status=resolved`，payload分别表达`approved=true/false`；只有不提交有效响应的取消才使用`status=cancelled`且省略payload。这是现有AguiResume的语义。
- 一次恢复覆盖服务端要求的全部未解决中断；多个中断可逐项选择，齐备后统一提交。
- 恢复沿用相同threadId、生成新runId；不新增一条伪造访客消息，不重复创建历史问题。
- 刷新后通过已鉴权的会话运行快照读取尚未解决的中断。该读取能力为拟新增；从现有协调器状态提供，不信任浏览器自行提供的“已批准”状态。
- 后端重启后若无法核验原中断，不静默放行，也不承诺无损恢复；提示确认状态已失效，走明确的取消/重新执行路径。

### 4.2 队列消费规则：C05

| 当前情况 | 下一条排队消息 |
| --- | --- |
| 正常完成，保存/对账已完成，无待处理事项 | 自动领取队首并执行 |
| 达到轮次上限、运行失败、断流、智能体不可用 | 保留队列，等待用户继续或重试 |
| 工具确认或业务提案未解决 | 保留队列，不自动发送 |
| 用户停止 | 保留队列，不自动发送 |
| 用户明确“引导/立即发送” | 完成目标运行的停止与收尾后，领取用户指定消息 |

普通输入在待确认期间可以继续排队，但不能作为resume响应。队列领取与移除必须发生在同一个归属校验边界；取消排队、停止和自动出队发生竞争时，不能静默丢消息或重复发送。会话切换后仍由运行store管理，不由某个已卸载组件的定时器管理。

## 5. 阶段三：保存与清空的一致性

### 5.1 读取详情与最终保存：C07

保留“前端提交 + 服务端兜底”的现有设计，本轮将它们接入同一个按runId去重的最终保存入口，不改为逐token写库。

- GET详情不再因MVC活动流已移除就立即flush。流结束后的待保存阶段与无主运行必须区分。
- 将异常运行清理移到受控的清理路径，复用现有persister调度能力；清理前核对活动运行、待保存记录及宽限时间，不能仅凭session.status或时间戳中断任务。
- 沿用当前15秒兜底宽限作为初始配置；正确性来自身份与幂等，不能靠延长宽限掩盖竞争。
- 前端正常提交与兜底保存都以sessionId+runId作为逻辑去重键。优先复用事件payload中的presentation.runId/parts.runId，不新增独立会话引擎或运行表。
- TimelineStore增加内部原子保存路径：同一数据库事务内检查已保存运行，再保存关联工具、用量和主回复；按现有数据库能力对会话写入串行化，不能只依赖JVM全局synchronized防重。
- 兜底已经保存时，迟到的同一运行正常提交返回已有记录。可核验的补充数据按稳定身份补齐，不能覆盖已经终结的原始内容或重复追加子任务步骤。
- 客户端与服务端内容不一致时返回明确冲突，保留本地内容；不能一律吞错。旧运行请求不能标记新运行已flush或释放其租约。
- 服务端已观察到的正常、受限、失败、取消和待确认终态分别保留，不把所有兜底保存都标成“中断”。缺少终态的情况才按未确认中断处理。
- 旧记录无runId时继续可读，不按正文内容强行合并；新写入路径必须有运行身份。

### 5.2 清空真实上下文：C06

两个入口——`/{sessionId}:clear`和斜杠clear执行——调用同一个应用清理流程。

1. 校验所有权，检查实际活动/准备/待保存/确认状态。与发送准入共享会话级互斥边界，不能只检查可能过期的数据库状态。
2. 删除路由前解析目标：绑定智能体、历史agent_route涉及的运行智能体，以及实际使用过的基础对话状态。保持userId+sessionId作用域，不能删除其他会话或整个智能体。
3. 先清理这些已确定目标的原生状态，再删除时间线和交付物。自由会话可能用过多个智能体，不能只删最后一个。
4. 数据库与文件状态不是同一事务；采用可重复执行的清理顺序。任一状态删除失败就返回失败，保留可重试的历史定位信息，不吞错并返回cleared。
5. 全部成功后才更新会话状态并清理前端缓存；失败时明确提示，保留页面内容。

## 6. 阶段四、五：回放、结果与性能

### 6.1 稳定步骤定位：C10

- 有parts的记录优先使用服务端/前端共享的稳定partId或其派生anchor，不再用seq+kind覆盖唯一身份。
- 老格式没有partId时，才按已验证为唯一的旧记录身份回退；多个候选时禁止全部指向同一个块。
- 保留当前锚点编码方式，回归同消息多个正文、多个工具、混合思考，以及翻页、折叠和高亮。

### 6.2 子任务状态与详情同步：C11

- 以id合并同一个子任务，用最新运行事件驱动状态、结束时间、结果和事实更新，不能用“是否仍运行”或“步骤是否更多”代替版本新旧判断。
- 分开处理“生命周期终态”和“过程内容完整度”：状态已完成不能被旧远端运行态覆盖，远端完整步骤也不能被空的本地步骤覆盖。
- 必要时在现有子任务视图中增加可比较的更新时间/事件位置，属于拟新增的只读投影字段；不以浏览器当前时间伪造服务端顺序。
- 收到落定事件时刷新或合并相应条目，不只监听任务数量变化；回放替换实时记录后保持选中子任务与阅读位置。

### 6.3 文件工具失败语义：C12

不能在前端笼统匹配`Error:`前缀：一个正常文件本来就可能包含这段文字。

- 在FilesystemTool调用文件系统取得明确错误结果的位置，向工具结果链路补结构化失败状态，复用已有ToolResultBlock/ToolResultState和应用AG-UI状态透出能力。
- 优先保留现有公开Java方法签名：使用现有注册/适配层或兼容包装入口传递状态；若无法保留，必须列出调用点和兼容变更，再进入框架公共方法调整，不能直接把String返回改掉而忽略调用方。
- 保留原始工具文本供模型和技术详情查看；前端主行、批次、整轮提示统一消费明确状态。
- 历史记录没有明确状态时使用中性“调用已返回”，不通过读取文件内容推断成功或失败，也不追写历史结果。

### 6.4 增量渲染开销：C13

- 在buildBlocks单次投影中先建立process/final的身份Set或Map，再线性筛选，消除已确认的嵌套some扫描。
- 一次投影内复用查询索引，避免对相同工具结果重复解析；维持现有稳定anchor与展示顺序。
- 先做上述局部优化，不直接引入虚拟列表或重写store。只有测量仍显示其他瓶颈时，才另提范围明确的优化。
- 使用固定500、1000、3000块数据测量单步增量投影，预热后记录中位数和较慢分位；比较同机器改前/改后及增长趋势，不以某次耗时冒充浏览器整体性能达标。

## 7. 前后端契约与兼容性

以下字段/语义标为“拟新增”的内容尚未实现。实施时先补契约测试，再同步两端。

| 入口 | 当前能力 | 本方案约定 |
| --- | --- | --- |
| POST /agui/run/{agentId} | threadId、runId、messages、forwardedProps | 普通发送保留；确认恢复使用现有resume数组；相同会话已有运行时拒绝新执行，绝不隐式替换 |
| RUN_FINISHED.outcome | 已有interrupts协议 | 前端完整保留中断信息；多个中断统一核对后恢复 |
| POST /api/advisor/sessions/{sessionId}:interrupt | 当前会话级中断 | 拟增加可选expectedRunId；新前端必传，身份不匹配返回409；旧调用的会话级行为保留兼容但仍鉴权 |
| GET /api/advisor/sessions/{sessionId} | session、entries、deliverables | 拟增加可选runtime快照，表达实际运行/收尾/待确认与中断详情；无副作用，不在GET中抢先flush |
| POST /api/advisor/sessions/{sessionId}/messages | visitor/advisor及parts/presentation | 新advisor提交按runId幂等；复用已有记录返回；结构非法400、身份/内容冲突409；所有权与现有404隔离语义不变 |
| 两个clear入口 | 返回cleared或冲突 | 共用清理实现；真实状态清理失败不能返回cleared；活动或待处理状态返回409 |

SSE准入冲突应沿用已有AGUI_INTERRUPT_CONTRACT_ERROR错误事件形状及可读提示；若希望改为HTTP409，需要保证发生在响应提交前，并补兼容测试。本方案不同时引入两套不一致的冲突解释。

兼容要求：

- 不删除或重命名既有AG-UI字段。新前端遇到旧后端缺少runtime快照时，保留本地状态并显示无法核验；不能自动认定成功。
- 新后端继续读取旧parts与无presentation的历史数据；按runId去重只用于有可靠身份的写入。
- 优先保留处理器、Controller和工具的现有公开入口，必要扩展使用新增重载/默认实现，补旧调用方编译与行为测试。
- MVC应用是本次故障入口；协议公共处理路径发生变化时，同时回归WebFlux入口，不能让修复破坏另一个传输层。
- 首选在现有payload和事务能力内完成，无数据库删列/重建。若实施发现必须增加唯一索引或持久化字段，先补迁移、旧数据处理与回滚说明，再执行该增量。
