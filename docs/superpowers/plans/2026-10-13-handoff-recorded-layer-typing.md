## 一、要解决的问题

**最终目标：会话界面按 DeepSeek 那套设计重做**（一轮折叠、思考行、工具行、输入区、子智能体）。现在的对话页交互、气泡、观感都不行。

界面要呈现的东西——思考内容块、工具调用的稳定标识、回合边界与结束原因、流式增量——**只有新引擎才产出**。所以界面重做之前，**引擎必须先真的替上默认路径**。

否则就是"换了界面、底层还是旧引擎"，呈现出来的东西依然不对。

**本步要解决的，就是"默认路径仍是旧引擎"这一件事。**

## 三、顺序（已修正）

v1.0 把"记录层类型化"排在第一步，理由是"架构最干净"。**那是整洁偏好，不是需求**——用户看到的差别不来自旧类在不在，而来自跑的是哪个引擎。

修正后的顺序：

### 第 1 步：先探底，把默认路径切过去

改默认配置，让 `HarnessAgent` 走新引擎，然后跑全量测试。

**这一步产出的是事实，不是判断。** 现在**没有人知道**切过去之后哪些能力真的缺——已知补了输入队列，未知的是恢复逻辑、管理端状态、子智能体那几处。

不要凭猜测先补一堆东西。**先测出缺口清单，再按清单补。**

验收：全量测试通过；或得到一份明确的缺口清单。

### 第 2 步：记录层改成写类型化事件

这是**消除双形状**的一步，也是**桥的葬礼**。

现状：记录层写的是不透明 JSON 载荷，新内核读的是类型化事件，桥在两者之间翻译。**同一份日志两种形状**，正是"说不清某次改动走的是哪条路"的根源。

做完之后只剩一种形状，**桥失去存在理由，不删就没法编译**——这比人为规定"不要用旧代码"可靠。

### 第 3 步：删旧实现

删掉桥、旧的日志实现、旧的 JSON 事件类型。约 28 个引用点跟着简化。

**这是唯一不可回退的点**，必须独立一次，便于定位问题。

---

## 四、第 2 步的施工细节（关键调研结论，省掉重新查）

### 4.1 转换只有一个收口点

记录层写事件**全部**经由 `SessionRecorder.append(String type, Object payload)`（约第 194 行），共 29 处调用点。它把载荷序列化成 JSON 后才交给日志。

**所以不用逐个改 29 个调用点**，只要改这一个方法产出的东西。

### 4.2 真正的扩散源是一个类型定义

旧 `SessionEvent` 的载荷字段是 **JSON 字符串**（`payloadJson`）。类型化载荷装不进去。

要改的是**这个类型**。改完之后，读该字段的地方必须跟着改——这才是"28 个文件"的由来。

| 读取方 | 读取内容 |
| --- | --- |
| `SessionViews` | 消息事件 → 派生历史 |
| `SessionProjection` | 检查点、未确定工具调用、活跃执行 |
| `SessionStateAccess` | 管理端状态快照与变更 |
| `SessionRecovery` | 中断收尾与取消 |
| `SessionTurns` | 回合与输入状态 |
| `SessionRecorder` | 幂等判断、消息去重 |

### 4.3 现成的对应表

桥 `NativeSessionLog.toSurfaceEvent` 已经把"旧形状 → 新形状"逐条写好。**照它改，不需要重新设计。**

| 旧 | 新 | 说明 |
| --- | --- | --- |
| `message/user` / `assistant` / `system` | 对应角色消息 | 已改名（C-1） |
| `tool/result` | 工具结果 | 同名，需类型化 |
| `request/prepared` | `request/header` | 已改名；需带 `reason` |
| `turn/start`、`turn/resumed` | `TurnStart` | |
| `turn/{status}`（六种） | `TurnEnd` + 结束原因 | 已统一（C-1） |
| `step/start`、`step/end` | `StepStart`、`StepEnd` | 需带回合与步骤号 |
| `run/start`、`run/end` | 不透明载荷 | **保留**：携带回合层没有的信息（coverage、停止请求） |
| `state/checkpoint` | **不再写** | 工作状态改由投影重建，独立立项 |
| `input/received`、`input/applied` | **输入事件族** | 已实现；「已应用」由位置表达 |
| `context/replaced` 等 | 表面替换 | 用 `SurfaceOp.Replace` |
| 其余（inbox、交互、子智能体、验证…） | 不透明载荷 | 扩展族，保留 |

### 4.4 两个已验证的实现细节

1. **位置属于记录，不属于载荷。** 类型化载荷没有序号。凡需要"这个载荷在第几位"的判断，必须在折叠时把**位置与载荷成对携带**。
2. **回合有两种命名。** 输入按**回合标识**（字符串）归属，工作时间按**回合序号**（数字）记录。二者的对应必须在折叠里显式处理，否则"已应用"永远判不出来。

## 五、验收

- 全量构建通过（含文档生成）；
- 格式检查通过；
- **旧测试全绿**——它们是"改对了"的证据（第 2 步期间一批断言旧事件名的测试会变红，**那批红测试就是待办清单**，不是失控）；
- 默认路径确实走新引擎（可由日志文件的实际内容确认）；
- 日志中不再出现 JSON 载荷字段。

## 六、已知风险

| 风险 | 说明 |
| --- | --- |
| 第 1 步可能暴露不止一个缺口 | 这正是第 1 步的目的：先拿到清单，不要凭猜测先补 |
| 第 2 步中途编译不过 | 改了类型定义，编译立刻在数十处报错。余量不足会停在不可编译状态 |
| 第 3 步不可回退 | 删了就只能往前走，必须独立一次 |
| 不要顺手做别的 | 每一步目标单一。工作状态（检查点）改造属独立立项 |

## 七、与最终目的的关系

```
本步（引擎替上默认） ──→ 界面重做（最终目的）
        ↑                        ↑
   底层不再是旧引擎          数据形状才是对的
```

**不要停在"引擎切过去了"。** 那只是让界面能呈现正确内容的**前提**，不是交付。
